## 0. Why this document exists before the code

Phase 11 adds two surfaces that *could* disagree with the inventory truth — a per-lot quantity and a per-serial custody count. A surface that can drift and is guarded by convention will drift. So each law below is carried by a **deferred COMMIT trigger or a foldable cache**, not by a code review, and each has a **named red proof**: a minimal mutation that must turn exactly that law red, naming exactly that refusal.

Five rules this project paid for, and which this plan obeys:

1. **A suite that cannot compile reports nothing.** A string literal broken across two lines once made 92 proofs unrunnable while the roster still reported `cases=92`; a textual case count cannot detect it, only a parser can. The Phase 11 gate parses every rostered file.
2. **A non-empty list names no law.** `expect(mutated).not.toEqual([])` proves something refused, never *which* thing refused. Every red proof below asserts the **specific refusal string**.
3. **Prove the mutation landed.** A `sed` that matches no line goes green and records a missing law as fine. Every mutation is diff-checked *before* its run is read.
4. **A comment citing a check is evidence of nothing.** Three times in one day a comment named a check that did not exist. No law below is satisfied by a comment.
5. **A green vitest suite is not a typecheck**, and a skipped step is `UNMEASURED`, never green. The gate runs format, lint and typecheck as their own named steps, in the exact form they were run.

Evidence classes are never mixed in one sentence: `PROVEN IN LIVE CODE` / `PROVEN BY TEST` / `PROVEN BY DATABASE CATALOGUE` / `DESIGN ONLY` / `SPEC ONLY` / `UNMEASURED` / `BLOCKED` / `WAITING_FOR_INTEGRATED_SURFACE` / `INTEGRATION_PENDING`.

## 0a. Where every mutation lands (PART 6)

The frozen-migration law is now explicit that a red proof **must never mutate a frozen migration, even temporarily**, and that **a proof requiring frozen-history modification is wrongly designed.** This project has already paid for that once: in Phase 5 a mutation harness wrote a planted defect into the real tree and only a landing check caught it, and a second harness left a frozen migration dirty while printing "tree clean" because its clean-check was narrower than its mutations.

So the mutation target of every proof below is named here, before any of them is written. Admissible targets are exactly four: a **scratch copy of Phase 11's own DDL or source text**, a **synthetic fixture**, a **temporary generated tree**, a **throwaway non-canonical clone**. `0000`–`0079` stay byte-identical on disk in this working tree; `0080`–`0086` are Phase 4's live candidates and are not mutated either.

| proof | what is mutated | where it lives |
|---|---|---|
| `R-L02` | a column added to Phase 11's own DDL text | scratch copy of the Phase 11 DDL |
| `R-SER-01` … `R-SER-03` | rows, inside a transaction | scratch cluster (data, not files) |
| `R-SER-04` | the `FOR UPDATE` on `stock_serials` — which is in **Phase 11's `CREATE OR REPLACE` body** (patch request §4), not in the frozen definition | scratch copy of the Phase 11 DDL, applied over an **unmodified** frozen prefix |
| `R-LOT-01` … `R-LOT-03` | rows and cache values | scratch cluster |
| `R-LOT-04` | the outbound pricing expression — again **Phase 11's replacement body**, never the frozen original | scratch copy of the Phase 11 DDL, over an unmodified frozen prefix |
| `R-FEFO-01` | `inventory_pick_lots`, a Phase 11 routine | scratch copy of the Phase 11 DDL |
| `R-REP-01` | a source-type registration attempt | scratch cluster |
| `R-REP-02`, `R-REP-03` | Phase 11 TypeScript modules and zod schemas | scratch copy of the Phase 11 source |
| `R-REP-04` | a Phase 11 relation definition | scratch copy of the Phase 11 DDL |
| `R-WAR-01` | the warranty triggers and chain, Phase 11's own | scratch copy of the Phase 11 DDL |
| `R-APP-01` | the canonicalization trigger, Phase 11's own | scratch copy of the Phase 11 DDL |
| `R-APP-02` | the validator's `FOR KEY SHARE`, the axis-in-use guard, the immutability condition — all Phase 11's own | scratch copy of the Phase 11 DDL, over an **unmodified** frozen prefix |

**The two that needed checking were `R-SER-04` and `R-LOT-04`**, because both mutate the behaviour of `inventory_apply_stock_movements`, whose current definition is in a frozen migration. They are admissible — the writer is re-created by Phase 11's own `CREATE OR REPLACE`, and that text is what the mutation edits — but they were admissible by accident until this section said so. The scratch cluster is built in two steps and the order is the proof: apply the frozen prefix **unmodified**, then apply the **mutated** Phase 11 DDL.

**And the harness check, learned the hard way:** the clean-check must be at least as wide as the mutations. Every proof run ends with a digest comparison over the **whole accepted prefix** plus `git status --porcelain` over the **whole tree**, not over the directory the harness happened to touch, and the gate's `frozen-prefix` arm runs **after** the suites rather than before them.

## 1. The laws

### L-P11-02 — no Phase 11 relation carries money
**Statement.** No relation created by Phase 11 has a column matching `value_%_minor`, `valuation%`, `unit_cost%` or `avg_%`, and no Phase 11 TypeScript module computes a monetary value from a lot or a serial. **A column labelled "report-only" or "non-authoritative" is not an exception** — `TL-P11-R2` and §55 refused exactly that proposal on serial rows, because non-authoritativeness is a hope about readers, not a property of a column. Acquisition cost is reached by **joining** through the movement the overlay already names.
**How it is checked.** Two independent ways, deliberately: (a) the migration's end-state assertion queries `pg_attribute` for the relations it created — `PROVEN BY DATABASE CATALOGUE`; (b) a gate arm parses the Phase 11 DDL text and the Phase 11 source tree. The text arm strips comments and string literals with the existing `stripCommentsKeepStrings`, **not a new lexer** — and the blanker itself gets a fixture test including a regex literal, because a blanker with no regex-literal handling once inverted quote parity for the rest of a file and made nine laws answer "no subject found" instead of "defect found".
**Red proof R-L02.** Two mutations. (a) Add `value_delta_base_minor BIGINT` to the lot overlay in a scratch copy; (b) add `unit_cost_base_minor NUMERIC(28,10)` to `stock_serials` **with a comment saying it is report-only** — the second is the one the first draft actually proposed, so it is the one the arm must catch, and a comment must not exempt it. In both cases the catalogue arm must raise `inventory.migration_end_state_invalid` naming that column, and the text arm must name the file and the column. Diff-checked first.

### C-SER-01 — serial custody equals on-hand
**Statement.** For every serial-tracked `(business_id, warehouse_id, variant_id)`: `count(stock_serials WHERE custody_state='in_stock' AND warehouse_id = w) = stock_levels.on_hand`, and `on_hand` is an integer.
**How it is checked.** Deferred constraint trigger at COMMIT, refusing `inventory.serial_custody_conservation_violated`; plus an executed reconciliation over a built fixture world.
**Red proof R-SER-01.** Delete one `stock_serial_events` row inside the transaction (as the internal owner, in a scratch cluster) and require that exact refusal at COMMIT. A variant: make `on_hand` fractional for a serial-tracked variant and require `inventory.serial_quantity_not_countable`.
**The trap.** The guard must derive its subject from the **movement's own `qty_delta`**, never from a visibility-dependent `count(*)` that would read `0` both when nothing exists and when RLS hides everything. A `SECURITY DEFINER` reads as its owner through one policy, so "absent" and "invisible" are one answer.

### C-SER-02 — the custody chain is append-only and alternating
**Statement.** `event_seq` is gap-free and monotonic from 1; directions alternate starting at `in`; `custody_state` and `warehouse_id` equal the chain's last event; a serial is `in_stock` in at most one warehouse.
**How it is checked.** Append-only trigger (UPDATE and DELETE refused) plus a deferred chain trigger. The one-warehouse part is structural: `CHECK ((custody_state='in_stock') = (warehouse_id IS NOT NULL))` with a single `warehouse_id` column, so two warehouses are unrepresentable rather than merely forbidden.
**Red proof R-SER-02.** Four mutations, four distinct refusals named: a gap in `event_seq`; two consecutive `out` events; a `custody_state` that disagrees with the last event; an attempted `UPDATE` of an existing event.

### C-SER-03 — every movement line of a serial-tracked variant carries exactly `abs(qty_delta)` events
**Statement.** As stated; direction matches the movement's sign; a non-tracked variant carries none.
**How it is checked.** Deferred constraint trigger, four refusals (`serial_assignment_missing`, `_count_mismatch`, `_direction_invalid`, `_forbidden`).
**Red proof R-SER-03.** For each of the four, one mutation naming that refusal. **And one more, which is the proof that matters:** a path that writes a movement for a serial-tracked variant with **zero** events must be shown to red. If any path can satisfy this trigger with zero events, the overlay drifts from on-hand silently and for ever — so the red proof enumerates the writer's own branches rather than one happy path, and the gate reds if a new writer branch appears without a case.
**This is the first law a challenger should attack.**

### C-SER-04 — a serial cannot be sold twice
**Statement.** Two concurrent commands consuming the same serial: exactly one commits; the other is refused `inventory.serial_not_available`.
**How it is checked.** Real PostgreSQL, two connections, a transaction barrier, the serial row locked `FOR UPDATE` inside the writer. **Never `sleep()`, never a JS object simulation.** The lock order is stated and tested: existing stock targets first (`inventory_lock_stock_targets`), then lots by `lot_id` ascending, then serials by `stock_serials.id` ascending — a suffix on the global order, never an interleave, and the deadlock test runs both orders.
**Red proof R-SER-04.** Remove the `FOR UPDATE`; both transactions must then commit and the test must fail naming the double sale. (Removing a lock is the mutation; the proof is that the *absence* of the lock is detected, not that the lock exists in the text.)

### C-LOT-01 — lot deltas sum to the movement delta
**Statement.** `Σ stock_lot_movements.qty_delta = stock_movements.qty_delta` for every movement of a lot-tracked variant; signs agree; a non-tracked variant carries no overlay rows.
**How it is checked.** Deferred constraint trigger, four refusals; it must survive `SET CONSTRAINTS ALL IMMEDIATE` (the Phase 3 R-94 finding: a guard that fails open under `IMMEDIATE` is not a guard).
**Red proof R-LOT-01.** Four mutations naming four refusals, plus one that runs the whole thing under `SET CONSTRAINTS ALL IMMEDIATE` and requires the same refusals.
**Status.** The overlay's own half is `PROVEN BY TEST` on the scratch cluster — **31 Pack B cases, 0 failed**, `EXIT_PROOFS_B 0`, at the SHA named in `P11-LIVE-DDL-PROOF.md` §8: the sum mismatch, the missing allocation, the sign disagreement and the forbidden overlay on a non-tracked variant are each refused by their own named error, and the `SET CONSTRAINTS ALL IMMEDIATE` case is refused identically. **Every movement in those cases was written by the OFFICIAL command** `inventory_adjust_stock`, not by the harness: a hand-written binding is refused by `inventory.stock_source_line_missing`, because the bridge the binding needs has exactly one writer and it demands a consumed assertion (defect 23). The integration half — the writer of §3.6 carrying the allocation — is **`WAITING_FOR_INTEGRATED_SURFACE`**: that change is not in this round, so nothing here claims the production write path.

### C-LOT-02 — per-lot on-hand never negative
**Statement.** A consumption exceeding a lot's on-hand is refused `inventory.lot_insufficient_stock` under that lot level row's lock, with no partial write.
**Red proof R-LOT-02.** Over-consume one lot while another lot of the same variant holds plenty: the refusal must be the per-lot one, **not** the variant-level `inventory.insufficient_stock` — a distinction that a test asserting merely "it threw" would miss entirely.
**Status.** The cache's own floor is `PROVEN BY TEST` (`stock_lot_levels_on_hand_ck` refuses a negative per-lot on-hand). The CONSUMPTION refusal is `SPEC ONLY` and stays so until §3.6's writer exists: there is no path that consumes from a named lot yet, and a refusal with no caller cannot be proved. Stated rather than folded into the line above it.

### C-LOT-03 — per-lot on-hand sums to the key's on-hand
**Statement.** `Σ stock_lot_levels.on_hand = stock_levels.on_hand` for every lot-tracked key, and the per-lot cache equals its fold from `stock_lot_movements`.
**How it is checked.** **Two** deferred constraint triggers, which is the correction the first independent challenge of Pack B forced: one on `stock_lot_levels` (the side that writes the cache) and — new — the comparison inside the movement-side trigger `stock_lot_movement_conservation`, which fires on **every** movement and has the key in hand. Both raise the same error name, because they are one law and not two. Plus `inventory_lot_verify` (`SPEC ONLY`) as the routine twin of `inventory_stock_verify`.

**WHICH PATHS THE LAW IS ENFORCED ON, and which it is not.** Asked for by name by the second independent challenge (`PB-17`), and owed:

| path | enforced? | by what |
|---|---|---|
| a movement is written | **yes**, at COMMIT | `stock_lot_movement_conservation()` |
| a cache row is written or updated | **yes**, at COMMIT | `stock_lot_level_conservation()` |
| **a bare `UPDATE stock_levels SET on_hand = …`** | **NO** | nothing: it is neither a movement nor a cache write, so it fires neither trigger |

Measured at `b7ee445`: from a consistent seed the key committed at 13.0000 against a cache of 3.0000, as `daftar_migrator` and as `daftar_inventory_internal`, rc=0 both times. **Pack B does not close that path and deliberately does not try**: a trigger on `stock_levels` would be Phase 11 guarding a FROZEN relation, and the frozen core makes the same bargain for its own conservation law — `stock_levels` carries only `stock_levels_retain` and `stock_levels_zero_on_hand_zero_value`, and the core's totals are checked against `stock_movements` by the ROUTINE `inventory_stock_verify`. The overlay inherits that bargain, and the gap closes where the core's closes: **`inventory_lot_verify` (§3.8, `SPEC ONLY`) is named here as the place**, owed the same slot in the reconciliation schedule as its core twin. The exposure is stated as a grant, measured at both granularities, because that is the honest form: **table-level `UPDATE` on `stock_levels` is held by `daftar_migrator` only, and `UPDATE (on_hand)` by `daftar_inventory_internal` as well** — which does not read as well as `C-LOT-06`'s *no runtime role holds `UPDATE` on `stock_lots` at all*, and that is the point of writing it down. A case asserts both lists, so a future grant that widens either reds a case.
**Red proof R-LOT-03.** Two mutations: perturb the per-lot cache directly as the internal owner (the sum trigger must red); and drop one overlay row (the fold comparison must red naming the lot). **A third, added because it is the one that fired:** remove the comparison from the movement-side trigger and a lot-tracked movement that moves the key away from the cache must commit — measured, 3 cases red, one of them judged as `daftar_app` (`NOSUPERUSER NOBYPASSRLS`) at COMMIT. **This was the second law a challenger should attack, and the challenger attacked it successfully** — a per-lot cache that can disagree with `stock_levels` is a second quantity truth wearing a cache's clothes, and the guard that existed watched only the side that writes the cache.
**Status.** `PROVEN BY TEST` for the cache-versus-key half **in both directions of reach** — written from the cache side and reached from the movement side — and the sentence that stood here before was **false as written**: it claimed *"a per-lot cache that does not sum to the stock key's on-hand is refused at COMMIT"* while a movement that moved the key away from a satisfied cache committed with the key at 12 against a cache of 8 (`P11-LIVE-DDL-PROOF.md` §10.1). Corrected rather than reinterpreted. **The scope of what is enforced is narrower than the statement above and is stated here rather than in a footnote:** a cache that EXISTS for a key must fold to that key; *every lot-tracked key HAS a cache* is `WAITING_FOR_INTEGRATED_SURFACE`, because the writer that maintains the cache is §3.6's and does not exist. `inventory_lot_fold` reads the **movements** rather than the cache, is no longer executable by PUBLIC (a role with no privilege on the overlay used to read quantities through it), and **refuses on both halves of its scope** — business and tenant — rather than answering a confident `0` to a caller whose rows row-level security has hidden. `inventory_lot_verify` as a routine is `SPEC ONLY`; the fold is what exists. **Concurrency for this law is MEASURED for the writers that exist, and was carried as `UNMEASURED` for a reason that did not hold.** The handoff said the second party — §3.6's cache writer — does not exist. The second independent challenge answered that it exists as a PRINCIPAL, because this pack's own end state grants `UPDATE (on_hand, last_movement_seq) ON stock_lot_levels TO daftar_inventory_internal`: *"the writer does not exist"* was a statement about the code, and the law is about whoever holds the grant. The four races are now in this pack's own harness (`prep/phase11/harness/races_b.py`, modelled on and credited to `challenge-b7ee445/pb3race.py`), run in the authoritative run, **0 findings**: `R1`/`R1b`, a key-mover against a cache-writer, each unlawful alone and their combination consistent-looking, are **both refused in both arrival orders**, each naming the sum it could see, with the committed state untouched — neither is rescued by the other's uncommitted work, which is the property that matters; `R2`/`R2b`, two lawful movements on one key through different lots, both commit with key = cache in both orders, the later transaction visibly blocked on the key row. **What remains `UNMEASURED` is narrower and is stated as such**: a cache writer that moves the cache WITHOUT moving the key and is lawful doing it, which no principal can be today because any one-sided change is refused on its own. That is §3.6's writer, and the lock order belongs with it. `SERIALIZABLE` and deadlock remain `UNMEASURED` for both packs.

### C-LOT-05 — a conservation check that cannot read its subject REFUSES
**Statement.** When **either** deferred conservation trigger cannot read the movement, its stock key or its product at COMMIT, it raises `inventory.lot_conservation_unverifiable` — *the law could not be evaluated* — and never returns silently.
**Why this law exists.** The first independent challenge of Pack B measured the opposite: the trigger's `NOT FOUND` arm returned `NULL`, so a COMMIT by a principal or in a context that could not SEE the movement skipped `C-LOT-01` entirely and a lot-tracked variant committed 7 units belonging to no lot. The comment justified the arm as a rollback accommodation, and that was measurably false — PostgreSQL discards the queued after-trigger events of an aborted subtransaction, so a rolled-back INSERT never fires its own constraint trigger. The arm was an RLS escape hatch with a comment on it. This is the project's twice-ruled class (Phase 5's fail-open deferred check, Phase 13's case 11) and the remedy is the settled one: **a fail-closed branch, not `SECURITY DEFINER`.**
**Red proof R-LOT-05.** Write the movement through the official command, then drop to `daftar_app` and `RESET` both context settings before COMMIT: the COMMIT must be refused by name. Mutation: restore the `RETURN NULL` arm and that case must commit — measured, it does. And the complement, so the law is not a refusal of everything: the lawful path must still commit, asserted on the committed state.
**The CACHE side had the same arm, and it was found here rather than reported (`D-32`).** Re-reading `stock_lot_level_conservation()` against the fix the challenge forced on its twin showed the same `IF NOT FOUND THEN RETURN NULL`, and the same consequence: the read runs under the invoker's row-level security, so a cache row written against a key the writer cannot see at COMMIT committed with no comparison at all. One thing the first draft of that comment got wrong and is corrected here rather than quietly: **the key cannot be genuinely absent.** `stock_lot_levels_level_fk` references `stock_levels (business_id, warehouse_id, variant_id)`, and a foreign-key check runs as the referenced table's owner and ignores RLS — so the FK, not the trigger, is what guarantees a cache row has a key behind it, and `NOT FOUND` means exactly one thing: *the row exists and this transaction cannot read it*. Which is why the red proof is an INVISIBILITY case, not an absence case: write the cache row lawfully as the internal principal, drop to `daftar_app` and `RESET` both context settings before COMMIT, and the COMMIT is refused by name. Mutation: restore the `RETURN NULL` and that case commits — measured. The end-state assertion pins the arm's presence in **both** functions' text, because the defect both times was that one of two sites had it.

**Status.** `PROVEN BY TEST`, on both sides. The refusal must also come from the LAW and not from a grant: a first version of the read took `FOR SHARE`, which needs UPDATE-class privilege that every writer of an append-only ledger deliberately lacks, and the COMMIT then failed `permission denied for table stock_movements` instead. Measured, reverted, recorded — a refusal is not the same refusal because it is also a refusal.

### C-LOT-06 — a lot's facts are frozen once the ledger names the lot
**Statement.** `expiry_date`, `produced_on`, `received_seq` and the lot code of a lot that any `stock_lot_movements` row names cannot be changed (`inventory.lot_facts_frozen`); a lot no movement names is still correctable; and `status` is never a fact of the goods, so a quarantine stays allowed.
**Why this law exists.** `UPDATE stock_lots SET expiry_date = '2099-01-01'` on an expired lot returned `rc=0`, and an `expiry_policy` that admits only `refuse` over a rewritable date is weaker than it reads. The pack never claimed otherwise, so this was a gap in the law set rather than a broken law.
**Red proof R-LOT-06.** Rewrite the expiry date and the receipt order of a lot with movements: both refused by name, **as the owner**, because the guard binds whoever can write exactly as the append-only law does. Mutation: drop the trigger and both commit — measured. Plus the complement on an untouched lot, and the quarantine case.
**Status.** `PROVEN BY TEST`. A case records that **no runtime role holds `UPDATE` on `stock_lots` at this SHA at all**, so the merchant-facing correction path needs a grant that does not exist yet; the guard is what that grant will be safe against.

### C-LOT-04 — the lot overlay is value-neutral (the law that makes the whole shape safe)
**Statement.** Consuming the same quantity of the same variant from lot A and from lot B produces the **identical** `value_delta_base_minor`, and the key's `valuation_base_minor` and `avg_unit_cost_base_minor` follow the pre-Phase-11 arithmetic exactly.
**How it is checked.** Executed on a live cluster: build one variant with two lots received at *different* unit costs, consume from each in two separate worlds, and compare the written values **against the values the pre-Phase-11 writer produces for the same movements** — an independent oracle, not the new code compared to itself.
**Red proof R-LOT-04.** Make the writer price the outbound from the lot's own receipt cost instead of the key's average; the comparison must red, naming both values. If this proof cannot be made to red, the overlay is not value-neutral and `ADJ-P11-01` has been answered by accident.
**Status.** The STRUCTURAL half is `PROVEN BY DATABASE CATALOGUE`: no column of a monetary name exists on any of the three overlay relations, asserted from `information_schema` rather than from the text, and `stock_levels` still carries no column below the variant. The ARITHMETIC half — the identical `value_delta_base_minor` from two differently-priced lots — is `WAITING_FOR_INTEGRATED_SURFACE` and is **not** claimed: it needs §3.6's writer and an outbound consumption, neither of which exists in this round. Noted because the executed cases deliberately use a **zero-value** receipt (defect 24: a valued document owes an accounting binding only the accounting authority may write), so no value arithmetic was exercised at all.

### C-FEFO-01 — the picker is a function, and refuses rather than guessing
**Statement.** `inventory_pick_lots(key, qty, as_of, policy)` is deterministic, reads no machine clock, orders by `(expiry_date NULLS LAST, received_seq, lot_id)` for FEFO and `(received_seq, lot_id)` for FIFO, and refuses `inventory.lot_selection_insufficient` with no partial pick.
**How it is checked.** Determinism is proved by repeated calls across differing plans (and with the rows physically reordered), not by reading the `ORDER BY`. Clock-freedom is proved by calling with two different `as_of` values and requiring two different answers, plus a parser arm that reds on `now()`, `current_date` or `clock_timestamp()` inside the routine body.
**Red proof R-FEFO-01.** Three: remove the `lot_id` tiebreak (two lots sharing an expiry and a `received_seq` must then be shown non-deterministic); replace `as_of` with `current_date` (the two-`as_of` case must red); return a partial pick (the refusal case must red). **Watch the tiebreak proof:** two rows that *happen* to come back in the same order prove nothing, so the fixture forces a physical reorder.

### C-REP-01 — a customer's device is never stock
**Statement.** No `stock_source_types` row names a repair intake; no `stock_movements` row exists for an intake; no Phase 11 relation holds a value for a customer-owned device.
**How it is checked.** Absence, proved three ways because absence is the easiest thing to "prove" vacuously: the migration end-state assertion over `stock_source_types`; a gate arm over the Phase 11 DDL text; and an executed attempt — register an intake source type in a scratch cluster and require the end-state assertion to raise.
**Red proof R-REP-01.** The executed attempt *is* the red proof, and it is the only form that counts here: an arm that merely greps for a string it wrote itself proves nothing.

### C-REP-02 — a repair part is consumed once, through the inventory authority
**Statement.** Consuming parts for a ticket writes exactly one `stock_movements` row per part line under the five-part identity, through `inventory_apply_stock_movements` and no other path, and its COGS posts through the existing accounting bridge with no Phase 11 journal logic.
**How it is checked.** Replay the same command twice: the second is idempotent (`replayed: true`) and writes no second movement — the existing `stock_movements_identity_uq` is what makes this structural. A source-tree arm asserts **zero** Phase 11 writes to `stock_movements`, `stock_levels`, `journal_entries` or any accounting relation.
**Red proof R-REP-02.** Add a direct `INSERT INTO stock_movements` to a Phase 11 module in a scratch copy; the arm must name that file and line.

### C-REP-03 — billing a repair part moves no stock and posts no second COGS
**The law the first draft needed and did not have (§60, `TL-P11-R7`); extended 2026-10-12 on PART 67.** Billing a consumed part through a preconsumed sale-line binding produces **zero** additional `stock_movements` rows and **zero** additional COGS postings; a binding cannot exist without the consumption it names; and **one consumption is billed at most once, for its full consumed quantity** — partial split billing of one consumption row is unrepresentable in v1, not merely refused.
**How it is checked.** Four executed cases on a live cluster, each counting rows **before and after** rather than inspecting code: bill a consumed part and require the movement count and the COGS posting count for that variant to be unchanged; attempt a **second** binding for the same consumption and require the primary key to refuse it; attempt a binding whose qty differs from the consumption and require `repair.billing_qty_mismatch`; attempt a binding **before** any consumption exists and require `repair.billing_without_consumption`.
**A fifth case, added on the Master Continuous Mission's §18:** a **retry** of the same billing attempt must **return the same original binding**, idempotently — not a refusal. This is a different property from condition 6, and the difference is the one that bites in production: a client that retries after a timeout must not be told its work failed when it succeeded. The case counts rows before and after the retry (unchanged), asserts the returned binding id is **the same row**, and asserts no second movement and no second COGS — and the red proof is the implementation that satisfies condition 6 by raising on the primary key without catching it, which is exactly how a correct uniqueness constraint produces an incorrect client contract.
**Three more cases, added on PART 67**, each for a condition the first eight did not carry: a binding whose ticket is **not** the ticket the consumption belongs to must be refused (`repair.billing_ticket_mismatch`) — and the fixture needs **two tickets**, because one ticket cannot fail this way; a binding whose **customer / custody context** differs from the consumption's must be refused (`repair.billing_custody_context_mismatch`), with a fixture carrying **two customers**, which is the case a single-customer fixture is structurally blind to; and a **partial** claim — `billed_qty` less than the consumption's `qty` — must be refused by the same `repair.billing_qty_mismatch`, with the structural half proved separately: the relation has **no quantity-claimed column** and is keyed one row per consumption, so a partial claim has nowhere to live. The structural half is the one that matters, because a refusal can be forgotten on a path while an absent column cannot.
**Red proof R-REP-03.** Put the part on an ordinary sale line instead of a binding — the exact defect of the first draft — and require the movement-count case to red naming **two** movements where one was expected. A test that merely asserts "the invoice was created" passes through this defect without noticing, which is how the draft got as far as it did.
**And the arm that matters most:** the request schema must have **no property** by which a client could supply a binding (conditions 1 and 2 of `P11-AL-21`). The proof is not that a supplied value is refused but that it is **unrepresentable**: add the property to the zod schema in a scratch copy and require a gate arm to name it. A refusal can be forgotten on one path; an absent field cannot.
**This is now the third law a challenger should attack**, alongside C-SER-03 and C-LOT-03 — and unlike those two, its failure mode is free inventory rather than a drifting count.

### C-REP-04 — no Phase 11 relation holds a customer money balance
**New, on PART 69.** A repair deposit is **canonical Phase 4 money** — an unapplied customer payment or a customer credit liability under the sealed Phase 4 contract — applied later to the repair sale through the canonical payment/credit allocation. Phase 11 creates **no deposit relation**, no repair receivable, no repair payment and no repair balance.
**How it is checked.** Absence again, and absence is checked structurally because it is the easiest thing to claim falsely: (a) the migration end-state assertion enumerates every relation Phase 11 created and requires that **none** carries a column matching `%amount%minor`, `%balance%`, `%deposit%`, `%paid%` or `%due%` — the same `pg_attribute` query that carries `L-P11-02`, widened; (b) a gate arm over the Phase 11 DDL text and source tree reds on a relation or module name containing `deposit`, `prepayment`, `advance` or `balance`; (c) a source arm asserting **zero** Phase 11 writes to any Phase 4 money relation (`payments`, `customer_credits`, `invoices`, `invoice_allocations`) — the repair module reads the customer's unapplied balance and writes none of it.
**Red proof R-REP-04.** Three mutations. (a) Add `repair_deposits (business_id, ticket_id, amount_minor, …)` to the Phase 11 DDL in a scratch copy: both the catalogue arm and the text arm must red, naming that relation and that column. (b) Add a Phase 11 module that inserts a `payments` row directly: the source arm must name the file and line. (c) Allocate a deposit to a **repair ticket id** rather than a committed invoice: the Phase 4 allocation path must refuse it, and the proof must show the refusal comes from **Phase 4's own authority**, not from a check Phase 11 added — because a Phase 11 check here would itself be the second authority the law forbids.
**The honest limit, stated rather than hidden:** Phase 4's payment and credit contract is not sealed, so (c) is `WAITING_FOR_INTEGRATED_SURFACE`. The design is settled; the surface it binds to is not, and this document does not call an unexecuted case proved.

### C-WAR-01 — a warranty is anchored, and its history is append-only
**New, on PART 70.** A warranty row exists only against a **committed sale**, one of **its own sale lines**, and the **serial/item where applicable**. Its issuance facts (`sale_id`, `sale_line_id`, `serial_id`, `starts_on`, `ends_on`, `source`) are never updated and the row is never deleted; a cancellation, an expiry or a return records a **new event** in an append-only chain whose transitions are a closed set — `issued` → `cancelled` | `ended` | `voided-by-return` — and the current state is derived from the chain's last event.
**How it is checked.** The anchoring is structural, not validated: composite `FOREIGN KEY (business_id, sale_id, sale_line_id)` to the sale line, so an unanchored warranty is unrepresentable, plus a trigger requiring the sale's status to be committed at issuance. Append-only is a BEFORE UPDATE/DELETE trigger refusing both (`warranty.history_immutable`), the `0060` identity-lock precedent reused. The chain is the `repair_device_custody_events` shape: gap-free `event_seq` from 1, a closed transition set, terminal states terminal, current state equal to the last event — a deferred COMMIT trigger, and the derived `current_state` column proved against its fold exactly as the stock caches are.
**Red proof R-WAR-01.** Six mutations, six named refusals. (a) Issue a warranty against a **draft** sale → refused. (b) Issue one whose `sale_line_id` belongs to a **different** sale → refused by the composite FK, and the proof must show it is the **FK** that refuses, not a trigger, because an FK cannot be bypassed by a new writer. (c) `UPDATE` an issuance fact → `warranty.history_immutable`. (d) `DELETE` the row on a return path — **the exact defect of the first draft** → the same refusal, and the proof asserts that after the return the row is **still there** with a `voided-by-return` event appended, because "the return succeeded" is what a test would otherwise check while the history quietly vanished. (e) A transition out of a terminal state → refused. (f) Perturb `current_state` directly as the internal owner → the fold comparison reds naming the warranty.
**This is the law whose failure is silent.** A deleted warranty row breaks nothing today; it breaks the claim six months from now, when the only question that matters is whether this unit was ever under warranty, and nothing in the database can answer it any more.

### C-APP-01 — the variant matrix is closed, canonical and unique
**Statement.** A **live** (non-archived) matrix product's variant `attributes` is exactly its registered axis set, every value is a registered active value, the canonical form is unique per product, base variants stay `'{}'`, **a combination never changes once written**, **an axis named by existing variants cannot be removed**, and — stated after the second independent challenge, which defeated the first clause with a single `INSERT` — **the axis set of a matrix that already has variants cannot be ADDED to either: a populated matrix's axis set is frozen, and an axis a matrix registers cannot be archived while it registers it.** The clause *"exactly its registered axis set"* is a claim about BOTH sides of the equality, so it is a claim about every transition that can change either side: a variant write, a removal from the registry, and an addition to it. Round 1 found the removal side unguarded; round 2 found the addition side unguarded; **round 3 found a third route to the same state through the variant side's own early return**; the words had been the same all along.

**The clause is now stated over the STATE rather than over the statements, because three rounds is enough.** The forbidden state is *a live matrix cell set plus a live non-base row outside it, both able to hold stock*. Every statement that can reach it, with the refusal each one gets:

| the statement | the refusal |
|---|---|
| `UPDATE` a cell's attributes to `'{}'` | `catalog.variant_matrix_immutable` (round 1, P0-01) |
| `UPDATE` them to any other combination | `catalog.variant_matrix_immutable` |
| `INSERT` a partial or foreign combination | `catalog.variant_axis_set_incomplete` / `catalog.variant_axis_unregistered` |
| **`INSERT` a `'{}'` non-base variant on a product that has a matrix** | **`catalog.variant_axis_set_incomplete` (round 3, `PA-01`)** |
| `INSERT` an axis under existing live variants | `catalog.matrix_axis_set_frozen` (round 2, P1-N01) |
| **`UPDATE … SET status='active'` on an archived cell whose grid has since grown** | **`catalog.variant_axis_set_incomplete` [deferred grid closure at COMMIT] (round 4, `P1-01`)** |
| `DELETE` / `UPDATE` an axis or a value in use | the four in-use guards, and the same deferred check at COMMIT |

**Round 4 found the fourth door, and it was opened by round 3's own remedy — so the law is no longer a list of statements at all.** The `status` filter round 3 added to the freeze guard (finding `PA-02`, and still correct) made a verb reachable that nothing watched: `UPDATE product_variants SET status='active'`. Measured by the challenger at `04d87b3`: archive both cells (permitted at zero stock), register a third axis (permitted — no LIVE variant, so not frozen), `UPDATE … SET status='active'` → rc=0, and the committed state was one live non-base variant naming two of three axes, holding 7.0000. The canonicalization trigger fires on `UPDATE OF attributes, is_base, product_id` — not of `status` — and 0061 fires only on the way INTO `archived`.

**The remedy is a state check at COMMIT, not a fifth verb.** `catalog_grid_closed_check(business, product)` recomputes the clause for one product — *every LIVE non-base variant names exactly the axis codes the product's matrix currently registers, and every axis and value it names is active in the business's registries* — and is called by four `DEFERRABLE INITIALLY DEFERRED` **constraint triggers**, on `product_variants`, `product_matrix_axes`, `product_attribute_axes` and `product_attribute_values`, for INSERT, UPDATE and DELETE alike. A verb nobody enumerated still lands in one of those four relations, and the check does not ask which verb was used. It is DEFERRED because building a grid writes the axes before the cells, so every intermediate state of that transaction names fewer cells than axes; an IMMEDIATE copy would refuse the ordinary act of creating a matrix product, and the end-state assertion therefore pins `tgdeferrable AND tginitdeferred` as well as the three statement kinds. Each refusal carries the tag `[deferred grid closure at COMMIT]`, so a reviewer can tell which layer answered.

**Blindness is a refusal, not a pass — and the FIFTH round measured that the first version of this paragraph tested the wrong fact.** The check asserted it holds `SELECT` on all four relations and raised `catalog.matrix_grid_unverifiable` otherwise — the Pack B `D-32` shape ("a check that cannot look must not reassure"). `has_table_privilege` answers a question about the **GRANT**; the condition that defeats a deferred check is **VISIBILITY**. All four relations carry `ENABLE` and `FORCE ROW LEVEL SECURITY`, and `app_bypass()` on this schema is a ROLE test (`CURRENT_USER = 'daftar_platform'`, `0013`/`0052`), not a GUC test, so a principal can hold `SELECT` on all four and read **zero rows** from every one. Measured: the fourth-door chain run lawfully, then `SET ROLE daftar_app` and `RESET` of the request context before `COMMIT` — `privileges true true true true`, `rows visible 0`, `rc 0 NOT REFUSED`, one live variant outside its grid. The premise written here before — that a writer must already satisfy `business_isolation` on what it wrote — is true of the WRITING session and says nothing about the COMMITTING one, and that gap was the whole exploit.

**What the law tests now: the session that judges must be the session that wrote — and the record of who wrote lives where the judged session cannot write it.** Four `AFTER … FOR EACH STATEMENT` triggers (`<rel>_01_grid_ctx`, all three statement kinds) append `current_user|app.business_id|app.tenant_id` to **`catalog_grid_ctx_ledger`**, one row per writing statement, and the deferred check refuses `catalog.matrix_grid_unverifiable` unless **every** identity this transaction recorded is the same **and** equal to the identity at `COMMIT`, naming the count or both identities. The sixth round is why that sentence reads the way it does: the fifth round kept the identity in `p11.grid_ctx`, a **custom GUC in an unreserved prefix that the judged session could set itself** — no grant, no check, `rc=0` — and "first write wins" then preserved the attacker's value, so one session-level `SET` forged every later transaction on a pooled connection with nothing beyond `daftar_app`'s own rights. The ledger's integrity rests on three ABSENCES, each asserted from the catalogue at install and each with a case of its own: no role may write `recorded_identity` (it is a server-evaluated column `DEFAULT`; the writing roles hold `INSERT (txid)` only), no role holding `INSERT` holds `UPDATE`, `DELETE` or `TRUNCATE`, and RLS pins every row to its own transaction. **Unanimity rather than first-write-wins is what makes a forged row harmless instead of decisive**, and it also refuses a transaction that wrote as A, wrote as B and came back to A to commit — which first-write-wins passed. One cause, one answer, the same answer for every statement kind. The privilege loop is **kept** — necessary, never sufficient. The remedy both the challenger and the coordinator preferred, a **read-back** of the row that queued the check, was implemented, measured and **REJECTED BY MEASUREMENT**: a lawful `INSERT`-then-`DELETE` transaction has nothing to read back, so the read-back refuses a transaction that broke nothing, and "absent" has two causes the function cannot tell apart — the finding itself one level down. A guard that refuses a lawful write is a worse defect than the one it closes.

**The per-verb guards are kept, and the pair-drop says why.** The BEFORE guards refuse at the STATEMENT, so a merchant is told which write was wrong while the transaction can still be corrected, and they refuse writes the state check cannot see at all (a value archived with no variant yet naming it, an axis removed from a matrix that has none). Measured as a pair-drop (`prep/phase11/harness/mutations/`, the P5 R9 lesson applied before a challenger had to): **M7** drops only the deferred check and reds **14 cases on pass 1 and 18 on pass 2, every one of them a `P1-01` case** (round 5's own four `P1-01/5` cases among them) — so no per-verb guard answers the fourth door; **M8** drops the four BEFORE guards and keeps the deferred check, reding **17 on pass 1 and 17 on pass 2**, several of them with the deferred check's own refusal in place of the statement guard's name, which is exactly the signal a pair-drop exists to give; **M9** drops both and reds **39 on pass 1 and 43 on pass 2**, and the race fixture can no longer be built at all (`EXIT=2`) — not because a race regressed, but because cases the dropped layers no longer refuse leave the fixture's own axes archived. **Every count here names its pass**, which is `P3-01` of the fifth round: the suites are run twice on one database on purpose, and the second pass starts from the state the first left behind. The set is closed over the two relations the state can be written from, and the committed-state case — *no live non-base variant of a matrix product names other than exactly its product's registered set* — measures the state itself rather than any one door. **That case is the one that would have caught all three rounds**, and it is the shape every later pack's closure law should take. **Round 4's correction to that sentence: the case as written measured the state after the suite's own writes, and no write in the suite un-archived anything, so it would NOT have caught the fourth door.** A state case is only as good as the transitions the suite performs before it; the suite now runs the same predicate again after an un-archive has actually happened, and the law's enforcement no longer depends on a case noticing, because the check itself runs at every commit that touches the four relations.

### C-APP-02 — the matrix invariants hold under concurrency, not only per transaction
**Statement.** Closure and uniqueness hold **after two concurrent transactions commit**, not merely inside each one.
**Why this law exists at all.** It did not, until V2 of the Master Continuous Mission refused the sentence this preparation carried: *"apparel has no concurrency to prove; it adds no deferred conservation trigger and no lock order."* V2's answer is the law: **"no locks, therefore no concurrency" is not a proof.** Running the races found two real holes that every single-transaction test passed over.
**How it is checked.** **Nine** races, two live backends, interleaved by sentinel, **no `sleep()`** — `prep/phase11/harness/races.py`:

| race | the interleaving | what it must show |
|---|---|---|
| A | two sessions insert the same combination | the loser **blocks** on the speculative insert and is then refused on `product_variants_matrix_uq`; exactly one row survives |
| B | one session deletes an axis while another inserts a variant naming it | they **serialize** (the validator reads the registry row `FOR KEY SHARE`), and **zero** variants name an unregistered axis after both commit |
| B2 | the same two statements in the **reverse arrival order** | the deleter **blocks** on the inserter's key-share lock and is refused `catalog.matrix_axis_in_use`; the committed state keeps both the axis and its variant. **Both arrival orders are required**, because the guard is a refusal guard and not a lock-order device: `TL-P4-COORD-R62` measured that a `BEFORE ROW DELETE` trigger cannot lock ahead of the row being deleted (`GetTupleForTrigger` locks `OLD` before the body runs), so the ordering must come from the **insert** side and the reverse order is the only one that exercises the guard's body |
| C | one session changes `attributes` while another inserts the variant's **first** stock row | no changed-combination-with-stock row can exist |
| D | one session inserts a variant naming a value while another **archives** that value row | the archiver **blocks** (which `FOR KEY SHARE` did **not** make it do — finding P1-03) and is then refused `catalog.attribute_value_in_use`; **zero** variants name a non-active value |
| E | the same, with a **DELETE** of the value row | the deleter blocks and is refused by the new guard; zero orphans |
| F | race E in the **reverse arrival order** | the inserter waits on the deleted row and is refused by its own registry read; zero orphans. Both orders are run for the value registry exactly as B/B2 do for the axis registry — the challenge found that races A..B2 all attacked the **axis** registry and none the **value** registry |

| G | one session inserts a product's **first** variant while another adds a **third axis** to its matrix | the axis write **blocks** on the variant side's SHARED transaction advisory lock on `(business_id, product_id)` and is then refused `catalog.matrix_axis_set_frozen`; **zero** committed variants name other than exactly the registered set. Row locks cannot order these two: the validator can lock only the matrix rows that **exist**, and the freeze guard cannot see an uncommitted variant — mutual invisibility, which is why the ordering is an advisory lock (shared on the variant side so a fifty-cell grid still generates in parallel, exclusive on the matrix side) and not a row lock |
| H | race G in the **reverse arrival order** | the variant write blocks, and then — this is the point — the freeze guard is **lawfully silent**, because when T1 added the axis the product had no variants at all. The invariant is held by the variant side's own completeness count, which in `READ COMMITTED` takes a fresh snapshot per statement inside a plpgsql trigger and so reads three registered against two supplied: refused `catalog.variant_axis_set_incomplete`. **A guard being silent is not a guard being absent, and only the reverse order shows which one you have** |

**Red proof R-APP-02.** Remove the `FOR SHARE` from the validator's registry read and race B must produce the broken closure; **weaken it back to `FOR KEY SHARE` and race D must produce a committed variant naming an archived value** (measured: at `1a8ba15` it did, and T2 did not even block); remove the value-registry in-use guard and races D and E must both produce orphans; **drop `product_matrix_axes_30_set_frozen` and race G must commit a third axis under a committed variant** (measured serially: 2 cases red, one of them the committed-state count reading 1 non-conforming variant); remove the advisory lock from either side and race G's axis write must stop blocking; remove the axis-in-use guard and **race B2** must produce a variant naming a deleted axis (B2 is the arrival order that exercises the guard at all); make immutability conditional on existing stock again and race C must produce the forbidden state. Mutation target: **scratch copy of the Phase 11 DDL**, never frozen history.
**Status.** `PROVEN BY TEST` on a scratch cluster — **9 races, 0 findings, each one now also asserting that its two backends held an open transaction at the same time** (`pg_stat_activity.xact_start`, read from a third connection; finding `P2-01` of the fourth round was measured on Pack B's races and three of these nine had verdicts of the same shape), at the SHA named in `P11-LIVE-DDL-PROOF.md` §1, after the fixes (three in the DDL, and two in the harness: race B2's first run named an unregistered axis value so its T1 never took the lock, and **the race harness itself used to `sys.exit(0)` unconditionally**, so a race that printed a finding still returned success — found by re-reading it for this round, with no failing race to expose it). Nothing is claimed beyond these nine interleavings at `read committed`; deadlock and `SERIALIZABLE` are `UNMEASURED`. **All nine run both backends as `postgres`**, so row-level security is bypassed inside the triggers during a race; the guards' behaviour under live RLS is covered by the two serial cases that run as `daftar_app`, not by a race.
**What race C taught, kept because the next overlay pack will face it.** A cross-table guard whose condition is the **absence** of a row cannot be made safe by locking: there is no row to lock, and only `SERIALIZABLE` gives a predicate lock. It was closed by **removing the class of failure** — unconditional immutability, owned entirely by Pack A — rather than by asking the inventory authority for a lock. The cheaper fix was a lock on a row that does not exist; the correct fix was to make the question unaskable.

## 2. The gate

`scripts/phase11-s<N>-gate.ts`, npm script `gate:phase11:s<N>`, an **unconditional** step of the required `backend` CI job with no `if:` and no `continue-on-error` — the `scripts/phase4-s4-gate.ts` shape: exported `CHECKS: readonly Check[]` of `{ id, title, run(root): string[], ok, note? }`, predecessor gates composed by **importing their assertions**, never by spawning them.
