# DAFTAR — Simplicity Standard / معيار البساطة

> البساطة **Requirement رسمي** (Master §3). Feature صحيحة تقنيًا لكنها معقدة = غير مكتملة. هذا المعيار قابل للقياس ويُستخدم في كل Design/UX Review.

## 1. الاختبار الأعلى

> هل يمكن لمستخدم غير تقني أن يفهم الشاشة وينفذ مهمته **بدون شرح**؟ إن كانت الإجابة "لا" → أعد التصميم.

## 2. قواعد قابلة للقياس

| # | القاعدة | المقياس |
|---|---|---|
| SIM-01 | بيع عادي كامل | ≤ 3 قرارات من المستخدم (منتج، دفع، تأكيد) وشاشة واحدة للسلة |
| SIM-02 | تحصيل دين | ≤ 3 خطوات من قائمة العملاء حتى النجاح |
| SIM-03 | طلب يدوي | عميل + منتجات + تأكيد فقط |
| SIM-04 | Primary Action | عنصر واحد بارز بصريًا في كل شاشة؛ يتعرف عليه مستخدم تجريبي خلال ≤ 5 ثوانٍ |
| SIM-05 | حقول إلزامية | لا حقل إلزاميًا إلا ما لا يمكن استنتاجه أو تأجيله (منتج: اسم + سعر فقط) |
| SIM-06 | مصطلحات تقنية | 0 مصطلحات تقنية/محاسبية في واجهة التاجر (Journal/Debit/Credit/Outbox/Tenant/Idempotency…) |
| SIM-07 | ازدحام Dashboard | ≤ 6 وحدات معلومات رئيسية فوق الطية، الأولوية: مبيعات اليوم، طلبات، ديون، أقساط، مخزون منخفض، إجراءات سريعة |
| SIM-08 | عناصر بلا وظيفة | 0 Buttons بلا Function، 0 Placeholders في أي Phase |
| SIM-09 | عناصر متقدمة | كل Advanced setting خلف مستوى ثانٍ، لا في المسار الأساسي |
| SIM-10 | تأكيدات | ≤ 1 confirmation في أي workflow، وفقط للحالات الأربع المسموحة |
| SIM-11 | اتساق الأفعال | نفس الإجراء = نفس الكلمة في كل الشاشات واللغات (Localization Glossary) |
| SIM-12 | Empty state | كل قائمة فارغة لها CTA واحد واضح |
| SIM-13 | رسالة خطأ | كل خطأ يجيب عن 3 أسئلة: ماذا حدث / هل بياناتي بأمان / ماذا أفعل |
| SIM-14 | ميزانية التعقيد | كل عنصر UI جديد له مبرر مكتوب في وصف الـPR |
| SIM-15 | Onboarding (X + لغة) | ≤ 5 خطوات، خطوة واحدة بمهمة واحدة لكل شاشة، ≤ 3 حقول لإنشاء الحساب، ≤ 3 حقول في خطوة الدولة (الدولة + العملة + لغة المتجر)، منتقي لغة الواجهة على الترحيب لا يضيف خطوة، CTA واحد واضح، و"تخطي" متاح — وفق المرجع البصري 02_Onboarding.png |

## 3. UX Friction Review (Master §10)

قبل قبول أي Workflow أساسي يُحسب ويُوثّق: عدد الشاشات، عدد الضغطات، عدد الحقول الإلزامية، عدد القرارات — ثم يُحاول التقليل دون المساس بـData Integrity.

## 4. SIMPLICITY AUDIT (قبل الإطلاق — Master §167)

لكل Core Flow: هل توجد شاشة يمكن حذفها؟ حقل يمكن إخفاؤه؟ إعداد يمكن جعله Default؟ مصطلح تقني؟ إجراء مكرر؟ زر غير ضروري؟ هل المهمة مفهومة؟

## 5. الحد الفاصل

البساطة **لا** تعني: إخفاء أخطاء، تخطي تأكيدات مالية خطرة، إزالة مراجع التتبع عن العمليات، أو تقليل Data Integrity. البساطة للمستخدم؛ والقوة والصرامة داخل النظام.
