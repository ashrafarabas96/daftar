# DAFTAR — Accounting & security invariant reference / مرجع الثوابت المحاسبية والأمنية

> **What this is.** One page that states each resolved accounting/security invariant, names where it is enforced, and names the test that covers it. It adds no decisions: `PHASE_2_ARCHITECTURE_LOCK.md` remains the decision record, and this page only reports what the repository actually does today.
>
> **Read the status column first.** Recompiled after slice **P2-S3** landed on `phase/2-accounting-core` (migrations `0044`/`0045`). P2-S2 froze first: `0040`–`0043` are in `MIGRATION_MANIFEST.json` at their accepted hashes and `frozenThrough` is `0043_accounting_invariants.sql`.
>
> **What P2-S3 changed, stated narrowly.** P2-S2 gave the journal its structure and gave nobody the ability to write to it. P2-S3 gives it **exactly one writer**, and moves posting **authority** from SPECIFIED to ENFORCED: the HMAC-signed Accounting Command Assertion, the in-database fingerprint recomputation, the actor and scope derivation that trusts no caller value, the date policy resolved in the business's timezone, idempotency, the atomic audit and outbox write, and the `financial_started_at` transition. What it did **not** do is create any operational source: manual adjustment, reversal and opening-balance *workflows*, periods, an FX registry and every domain table remain SPECIFIED, and there is no generic posting HTTP endpoint.
>
> `0044` and `0045` were candidate migrations when that paragraph was written; they were accepted and frozen with P2-S3, and the frozen boundary has since moved through `0047` (P2-S4) and `0048` (P2-S5). The status column below is current; this header is kept as the record of when the page was recompiled.
>
> **The correction of 2026-09-22, stated before anything else on this page.** Tech Lead review of P2-S3 found two defects that this page, in its previous revision, would have led a reader to believe were impossible. The first: every elevated routine in the repository pinned `search_path` without naming `pg_temp`, and PostgreSQL searches the session temporary schema for relation and type names whether or not it is named — searching it **first** when it is not. A stolen `daftar_app` credential could therefore create its own `accounting_assertion_keys`, grant the elevated principal access to it, and have the verifier check signatures against a key it chose. It forged a journal entry; the reproduction is kept as a permanent regression. The second: `accounting_post_entry` resolved each account, then wrote the line, with nothing holding the account still in between, so a concurrent rename, retype or deactivation could land inside that window. Both are closed in the candidate migrations and in `bootstrap.sql`; the rows below say how, and `PHASE_2_S3_ACCEPTANCE.md` §10 is the full account.

## 1. Bidirectional source integrity (AL-01)

**Rule.** Every posted journal entry corresponds to exactly one registered business-fact identity, and that identity cannot disappear afterwards. Enforced by two `DEFERRABLE INITIALLY DEFERRED` foreign keys — `journal_entries → accounting_source_bindings` and back — both verified at COMMIT, both composite on `business_id`; binding rows carry no DML grant to any runtime role and a `BEFORE UPDATE OR DELETE` trigger.

**Status: ENFORCED (P2-S2).** `0042` creates `accounting_source_bindings` and both deferred directions: `accounting_source_bindings_entry_fk` (binding → entry) and `journal_entries_binding_fk` (entry → binding), each composite on `business_id` and each `DEFERRABLE INITIALLY DEFERRED`, so either row may be written first and neither may reach COMMIT alone. `accounting_source_bindings_no_mutation` (`BEFORE UPDATE OR DELETE`) makes the binding unchangeable, and no principal holds DML on it. The registry itself is closed: `source_type` is a foreign key into `accounting_source_types`, which holds exactly `opening_balance`, `manual_adjustment` and `reversal`.

**Tests.** `tests/integration/accounting-journal.test.ts` — Matrix 2 case H (entry with no binding → COMMIT FAIL), the reverse direction (binding with no entry → COMMIT FAIL), both orders inside one transaction passing, a binding pointing at another business's entry refused, a duplicate source identity refused, a second binding for the same entry refused, and an unregistered `source_type` refused. The migration text itself is checked in `tests/integration/accounting-guards.test.ts` ("the source binding keeps both deferred foreign-key directions"), so removing one direction fails CI even before a database starts.

**Honest residual, already admitted in the lock and still unclosed:** proof #3 is physical only for the *binding* row. A domain's *detail* row is protected by a per-table `BEFORE DELETE` trigger plus a registry-completeness test that enumerates `accounting_source_types`. That test is the whole guarantee for every future source type, and it does not exist yet — it should land in the same slice as the first detail table, not later.

## 2. Actor and scope anti-spoofing authority (AL-03, AL-04)

**Rule.** `accounting_post_entry` trusts no GUC, no caller-supplied actor UUID and no client permission claim. Authority comes from a signed Accounting Command Assertion — `v1.<kid>.<actor>.<tenant>.<business>.<operation>.<source_type>.<source_id>.<fingerprint>.<exp>.<jti>.<hmac>` — verified inside the database against `accounting_assertion_keys`, a table with no grants at all. 60-second expiry, single-transaction use, separate key namespace from provisioning. Actor shape is `('user'|'system')` with a CHECK; membership is defence-in-depth, never the proof of identity. Branch scope restricts which `branch_id` a scoped member may put on a line, checked inside the primitive.

**Status: ENFORCED (P2-S3).** `0044` creates `accounting_assertion_keys` (kid primary key, a `BYTEA` secret with a ≥32-byte CHECK, `active`/`retired`) and `accounting_assertion_uses` (the `jti` replay registry carrying the consuming transaction's `XID8`). Neither table carries any grant to any runtime role, so no credential a service authenticates as can read key material. `0045`'s `accounting_actor()` verifies the twelve-component assertion inside the database — HMAC over the first eleven components, 60-second TTL, single-use `jti` scoped to the transaction — and returns the actor, tenant and business out of the *verified* claims. `accounting_post_entry` reads authority from that return value and from nothing else: `app.business_id`, `app.tenant_id`, `app.user_id` and every other GUC a stolen credential could set are not consulted for authority, and a caller-supplied actor id does not exist in the payload schema. The key namespace is separate from provisioning, and `apps/api/src/config.ts` refuses to start when the two secrets are byte-equal. Branch scope is applied by `accounting-posting.service.ts` against the caller's membership before the command is signed.

**Tests (P2-S3).** `tests/security/accounting-posting-authority.test.ts` — no assertion, forged signature, tampered actor under a genuine signature, expired, wrong operation kind, wrong business, wrong tenant, replayed `jti`, a genuine assertion for another business, spoofed GUCs, and a payload that does not match the signed fingerprint. `tests/integration/accounting-posting.test.ts` covers the payload schema and the account rules.

The provisioning mechanism this followed, still live and still tested:

| piece | where |
|---|---|
| key table readable by nobody | `infrastructure/database/migrations/0038_provisioning_assertions.sql:41`–`:47` (`CREATE TABLE ... ; REVOKE ALL ... FROM PUBLIC`, no grants to anyone) |
| in-database verification | same file, `provision_actor(TEXT[])` at `:80` — HMAC over claims 1–6 at `:107`, expiry at `:120`, single-use `jti` + `pg_current_xact_id()` at `:127` |
| key management restricted to `daftar_platform` | same file `:72`–`:75` |
| minting, API side, 60 s TTL | `apps/api/src/infra/provisioning-assertion.ts` |
| owner authority from role identity, never a request flag | `packages/domain-core/src/permissions.ts` (`trustedRoleSet`, `is_system AND key='owner'`) |

**Tests (Phase 1, passing).** `tests/security/provisioner-boundary.test.ts` — no assertion `:220`; old-GUC spoof `:226`; forged assertion `:234`; tampered actor under a genuine signature `:246`; expired `:255`; wrong operation kind `:262`; cross-transaction replay `:275`; valid assertion but non-owner `:292`; key secrets unreadable by every principal including `daftar_platform` `:352`. Branch scope: `tests/security/branch-scopes.test.ts:124`–`:212`. Owner identity: `packages/domain-core/test/domain-core.test.ts:285`, `:291`.

**The name-resolution half, added in the 2026-09-22 correction.** Everything above is true about *values*: no GUC and no caller field carries authority. It was not true about *names*. `accounting_actor()` names `accounting_assertion_keys`, and the caller decided which relation that name reached, because `TEMPORARY` on the database is granted to PUBLIC by default and `pg_temp` is searched ahead of an unnamed path. The boundary is now a privilege, not a path: `bootstrap.sql` revokes `TEMPORARY` on the database from PUBLIC and from all six runtime roles, and `CREATE ON SCHEMA public` with it, which covers the frozen Phase 1 routines whose bytes may not change. Defence in depth sits on top of it — every non-frozen routine pins `pg_catalog, public, pg_temp` with `pg_temp` explicit and last, `0045` §9b repairs the *effective* paths of the frozen routines by `ALTER FUNCTION`, and guard **G-5** refuses both shapes in review. Proved live in `tests/security/search-path-shadowing.test.ts`, whose first section is the original exploit, inverted: it must be refused, and it must leave the journal empty.

**Gap to close when AL-03 lands:** Phase 1's assertion binds actor and operation kind. The accounting assertion additionally binds tenant, business, source type, source id and the posting fingerprint, and the primitive must **recompute** that fingerprint from the submitted payload and require equality before any write, refusing with `accounting.assertion_payload_mismatch`. None of that has a test yet, and the payload-mismatch case is the one that cannot be inherited from the provisioning suite: Phase 1 has no equivalent, because provisioning assertions carry no payload hash.

## 3. Writer exposure ordering (AL-18)

**Rule.** Every slice is independently safe. Structural schema may land before its writer; a writer may not land before every verification, binding, fingerprint, audit and outbox protection it depends on. `GRANT EXECUTE` on `accounting_post_entry` happens in exactly one slice (P2-S3), the one where all of them are present. P2-S2 ships the journal tables with the full REVOKE shape and no writer at all.

**Status: SPECIFIED, and honoured once.** Lock AL-18. This is a process rule about commit ordering, so nothing can enforce it mechanically; what *can* be checked is that a released tree never contains a writer without its protections.

P2-S2 was the ordering rule's first exercise and it held: the journal tables landed with the full REVOKE shape and no writer at all. P2-S3 is the second, and the converse is now checked rather than asserted. **Guard G-4** (`scripts/guards/posting-surface.ts`, static-guard Rule 17) states the rule as an implication: *if* `accounting_post_entry` exists in the tree, then all twelve of its protections must exist with it — assertion verification, fingerprint recomputation, source binding, audit, outbox, the `SECURITY DEFINER` shape, the internal owner, the REVOKE from PUBLIC — and the primitive must be granted `EXECUTE` to `daftar_app` and to nobody else, with no application file writing a ledger table directly. G-1 says the runtime-DML half from the grant model's side; G-4 says it from the writer's side, so deleting either one does not silently delete both.

One correction this slice had to make: two checks written while no writer existed asked the *live database* whether one did — `tests/security/accounting-boundary.test.ts` and the P2-S2 gate's slice-boundary check. Both were rescoped to the text of the frozen files they are actually about. A permanent predecessor gate that forbids its authorized successor is a gate that stops the project, and that is itself part of AL-18's discipline.

**Tests.** `tests/security/journal-privilege-matrix.test.ts` proves the no-writer state against the live database: no routine is callable by any runtime role or by PUBLIC, and no function body in `pg_proc` writes a journal table. The release gate (`scripts/phase1-release-gate.ts`, `scripts/phase1-gate.ts`) is per-phase and has no equivalent for this rule. The lock now records the missing check as **guard G-4**, due in P2-S3: if `accounting_post_entry` exists in a released tree, its assertion verification, source binding, fingerprint recomputation, audit and outbox must exist too. Until that guard is written, the governing rule remains a habit rather than something CI can refuse.

## 4. Opening balance lifecycle (AL-13)

**Rule.** `draft → posted → superseded`, plus `draft → discarded` (row deleted, no entry ever existed). After `posted`: lines, `as_of_date`, `journal_entry_id` and `id` are immutable; `status` is the only mutable column and only for `posted → superseded`; supersession requires an existing reversal of that opening balance's journal entry (`accounting.supersede_without_reversal` otherwise); the transition is audited in the same transaction; no runtime role holds UPDATE. `CREATE UNIQUE INDEX ... WHERE status = 'posted'` gives exactly one current set per business **at any instant** — a bound on what stands, not on how many opening balances a business has posted over its life, because the lifecycle above allows `posted → reversal → superseded` and then a replacement set. P2-S6 is what stops that lifecycle from reaching behind closed books: while ANY period of the business is closed, a NEW opening balance dated before the earliest period is refused with `accounting.period_closed_history`. The equity plug is an explicit visible line to `opening_equity`.

**Status: SPECIFIED.** Lock AL-13. No table, no trigger, no state machine in code.

**Tests.** None. The lock names eight cases (edit lines after posting, change `as_of_date`, change `journal_entry_id`, supersede without reversal, supersede with reversal, `superseded → posted`, two posted sets, plug line including the zero case).

## 5. Posting-date semantics (AL-14)

**Rule.** Future-dating is forbidden for every source in Phase 2: `entry_date ≤ today` resolved in the business's own timezone (`businesses.timezone`), never the server's. Lower bounds are per source and declared as data on `accounting_source_types`: `opening_balance` — none; `manual_adjustment` — none in Phase 2, back-dating permitted and audited; `reversal` — not earlier than the original entry's date. The `created_at − 10 years` floor is withdrawn. Periods are slice P2-S6; a business that has created one is additionally gated by it.

**Status: PARTLY ENFORCED (P2-S2) — the policy is data, the gate is not built.** `0042` creates `journal_entries.entry_date DATE NOT NULL` and `accounting_source_types` carries the bounds **as data** rather than as branching code: `lower_bound_policy` (`none` | `not_before_origin`) and `upper_bound_policy` (`not_after_today`), both CHECK-constrained, seeded as `opening_balance`/none, `manual_adjustment`/none, `reversal`/`not_before_origin`, with a migration-time assertion that every row refuses future posting. A new source type therefore cannot be added without declaring its date policy.

**Status update — ENFORCED (P2-S3).** `accounting_post_entry` reads `businesses.timezone` under the same row lock that holds the base currency stable, resolves the civil date in that zone, and refuses `entry_date > today` with `accounting.entry_date_in_future`. The lower bound is read from `accounting_source_types` as data — the routine contains no branch per source type — so `manual_adjustment` may be back-dated and a `reversal` may not be dated before the entry it reverses.

**Status update — the PERIOD gate exists (P2-S6, migration `0049`, accepted and frozen).** Stated truthfully, because it is narrower than the sketch above promised and the difference matters.

Periods do NOT become "the authoritative gate" for everyone. They become an ADDITIONAL gate, and only for a business that has created a period. `0049` creates no period for anybody, so a business with zero periods is subject to exactly the P2-S3 rules described above and nothing else — shipping the migration changes nothing for any existing merchant. A migration that had invented a fiscal calendar would instead have started refusing postings for people who never asked for periods, which is why the activation is opt-in by first use.

Once a business has at least one period, `accounting_period_guard_posting()` — a `BEFORE INSERT` trigger on `journal_entries`, so it binds every writer including a direct `INSERT` — requires each NEW entry's `entry_date` to fall inside exactly one existing period: none covering it is `accounting.period_missing_for_date`, a closed one is `accounting.period_closed`. Non-overlap is a physical gist `EXCLUDE` constraint, so "exactly one" is a fact rather than a hope.

**The shape of the set, not only the date of the row (P2-S6, second review round).** "An entry dated inside a closed period is refused" is true and insufficient: it leaves an OPEN period held behind a CLOSED one, a new EARLIER period created behind closed books, and a new opening position dated before them — three ways to change balances already declared final without writing a single row inside a closed period. So, per business and sorted by `start_date`, the periods are **zero or more CLOSED followed by zero or more OPEN**, contiguous. `accounting_period_topology_check()` enforces that as a **DEFERRABLE INITIALLY DEFERRED constraint trigger** on `accounting_periods`, judged at COMMIT because both halves are properties of the whole set; a transaction that would leave `OPEN CLOSED`, `OPEN CLOSED OPEN`, `CLOSED OPEN CLOSED` or a gap does not commit, for any writer, the schema owner included. Four command-level refusals give the merchant a sentence about their books in front of it, and replace nothing: close runs **oldest to newest** (`accounting.period_close_order`), reopen runs **newest to oldest** (`accounting.period_reopen_order`), no period may be created before the earliest while any is closed (`accounting.period_prepend_closed_history`), and no NEW entry may be dated before the earliest period while any is closed (`accounting.period_closed_history`, deliberately not `accounting.period_closed`, because the date lies outside every period). Neither close nor reopen cascades to a period nobody named.

**The one source-specific exception, and it is this section's business rather than the period slice's.** An `opening_balance` whose `entry_date` is strictly before the earliest period start posts without a covering period. That is the AL-14 sentence above — `opening_balance` has `lower_bound_policy = 'none'`, no historical floor, because an opening position can be any age — carried through the period layer instead of being quietly overridden by it. Without the exception the coverage rule would have made the SAME opening balance valid or invalid depending on whether the merchant created their first period before or after stating it, and an accounting fact must not depend on the order somebody configured the product. The exception is bounded on every side: strict `<`, so the earliest start date itself stays under the ordinary covering rule; inside a CLOSED period the opening balance is refused like anything else; after the chain it is refused for want of coverage; **once any period is closed it is refused outright with `accounting.period_closed_history`**, so the exception can never introduce new truth behind closed books; the no-future rule is untouched; and no other source has it, so a `manual_adjustment` or a `reversal` dated before the earliest period is refused. Proved in `tests/integration/accounting-periods-opening-balance.test.ts`, whose first two cases are the same fact entered in the two possible orders, ending in a comparison of the two businesses' posted entries.

Three things this does NOT do, each worth stating because each could be assumed. It does not relax the no-future rule: `entry_date ≤ today` in the business's timezone still holds INSIDE an open period, enforced by the frozen P2-S3 writer, which `0049` does not touch. It does not rewrite history: entries posted before the first period existed are never revisited, and no period is invented to cover them. And it does not block an idempotent REPLAY of an entry posted before a later close — the primitive returns from its own registry before it reaches the insert, so the guard never fires for one.

**Tests.** `tests/integration/accounting-posting.test.ts` — an entry dated after today in the business timezone refused, a back-dated manual adjustment permitted, "today" read in the business timezone rather than the server's, and a reversal dated before its origin refused and on-or-after permitted. `tests/integration/accounting-periods.test.ts` carries the period half: zero periods change nothing, the first period activates, the posting matrix (inside open, on either exact boundary, outside all, inside closed, for two different source types), the idempotent replay succeeding after a close, and a future date inside an OPEN period in `Pacific/Kiritimati` still refused with `accounting.entry_date_in_future` — the case that proves the two rules compose rather than replace each other. `tests/integration/accounting-concurrency.test.ts` §43 is the boundary test the rule really needed: `Pacific/Kiritimati` (UTC+14) and `Pacific/Honolulu` (UTC−10) are a full day apart at every instant, so "today in Kiritimati" is always a future date for a Honolulu business — and the suite proves the posting evaluates under whichever timezone the row lock gave it, in both race directions, with no permanent timezone lock invented.

## 6. Privilege matrix vs invariant matrix (AL-02)

**Rule.** Two separate matrices, and a PASS requires both. **Matrix 1 (privilege):** for each of the six runtime roles, direct INSERT/UPDATE/DELETE on `journal_entries`, `journal_lines` and `accounting_source_bindings` must fail with *permission denied*. **Matrix 2 (invariants):** executed as the schema owner so the constraint itself is exercised — A zero lines, B one line, C unbalanced, D balanced (PASS), E foreign-business account, F DELETE a posted line, G UPDATE a posted line, H entry with no binding. The entry-side deferred constraint trigger is the crux: it fires at COMMIT even when a transaction writes an entry and no lines.

**Status: ENFORCED (P2-S2).** Both matrices exist and both run in CI, as separate suites so that neither can be mistaken for the other.

**Matrix 1** — `tests/security/journal-privilege-matrix.test.ts`. The enumeration the lock asked for: the live catalogue is read twice, once through `information_schema.role_table_grants` and once through `aclexplode(coalesce(relacl, acldefault('r', relowner)))` (the unfiltered form, which sees grants to roles the first view hides), and both are compared against the intended model in `scripts/guards/journal-privilege-model.ts`. Anything present that is not intended fails, and anything intended that is missing fails. Three tamper cases prove the comparator itself notices an added INSERT, a removed SELECT and an opened registry. The hand-written adversarial half stays alongside it: six roles × three tables × three verbs, each expecting *permission denied for table*.

**Matrix 2** — `tests/integration/accounting-journal.test.ts`, executed as the schema owner so the constraint is what refuses, not a grant. A permission error must never be able to masquerade as invariant coverage, which is exactly why the two suites are separate and Matrix 2 runs as the owner.

**Tests (Phase 1, passing).** `tests/security/db-privileges.test.ts` — `daftar_app` bypass flag does nothing `:44`, cross-business read `:57`, cross-business write `:73`, DDL impossible `:84`, RLS cannot be disabled `:92`, revoked grants `:103`–`:146`; `daftar_identity` separation `:178`–`:260`. `tests/security/provisioner-boundary.test.ts:55`, `:66` cover the provisioner's grant shape.

**Managed-PostgreSQL portability (P2-S1).** `0039` → `0040`/`0041` is proven to apply over a `NOSUPERUSER`, `NOBYPASSRLS` migration principal in `tests/integration/migration-portability.test.ts`. Writing that test found that the `0040` backfill would have been a silent no-op under a non-superuser migrator, because `businesses` FORCEs RLS and no policy admits a deployment principal; the backfill now runs under the seeder's own identity. **Still open, recorded not fixed:** `0032`/`0033`/`0038` transfer function ownership to `daftar_platform`, which a non-superuser migrator can only do if that LOGIN runtime role holds `CREATE` on `public` — so the frozen Phase 1 history is not yet portable, and fixing it in place would undo the P2-S1 authority correction. See `docs/PHASE_2_S1_ACCEPTANCE.md` §6.

**Closed in P2-S1 for the chart:** `tests/security/accounting-boundary.test.ts` enumerates `information_schema.role_table_grants` for `accounts` and `accounting_system_account_keys` and asserts the whole shape, and runs a DML-denied and an EXECUTE-denied matrix across all six login roles; `scripts/guards/authority-isolation.ts` refuses the same violations from the migration text before any database starts — extended in P2-S2 with a rule that any write grant on a journal table, to anyone, is a violation.

**Closed in P2-S2 for the journal: guard G-1.** The intended matrix lives as data in `scripts/guards/journal-privilege-model.ts` — `daftar_app`, `daftar_platform` and `daftar_worker` hold SELECT on the three journal tables, `daftar_accounting_internal` holds SELECT so the deferred validators can see a whole entry, `daftar_identity`/`daftar_resolver`/`daftar_provisioner` hold nothing, the two registries are granted to nobody, and no grantee holds any write privilege anywhere. The model is compared against the live catalogue rather than restated in tests, so a `GRANT` added years from now by someone who never read this page still fails CI. `npm run gate:phase2:s2` additionally refuses the model itself if it ever starts describing a writer.

## 7. Fingerprint canonicalization (AL-11)

**Rule.** `posting_fingerprint CHAR(64)` = SHA-256 over canonical bytes `acctfp/1`, never `JSON.stringify()`. Fields `\x1f`-separated, lines `\x1e`-terminated; lowercase canonical UUIDs; account identity = `system_key` else `code:<code>`, never the display name or surrogate id; side `D`/`C`; amounts as bare decimal integers; uppercase ISO-4217; `fx_rate` always 10 fraction digits including `1.0000000000`; `fx_rate_at` RFC 3339 UTC seconds; NULL is the single byte `\x00`; lines sorted by their own serialized bytes; UTF-8. Description, memos, request id, actor and timestamps are excluded as narrative. FX rate, source and timestamp are *inside* the fingerprint, so a changed rate is a conflict, not a silent replay. Idempotency: `UNIQUE (business_id, source_type, source_id)`; identical retry → `created=false`; materially different → `accounting.idempotency_conflict` / HTTP 409, never silent success.

The fingerprint a caller presents is never believed on its own: `accounting_post_entry` recomputes the canonical form from the submitted payload inside the database and requires it to equal the fingerprint the assertion signed, refusing with `accounting.assertion_payload_mismatch` before any write (AL-03). The canonicalization is therefore implemented twice — TypeScript and PL/pgSQL — and the two must agree byte-for-byte.

**Status: ENFORCED (P2-S3).** `acctfp/1` is implemented twice against one specification: `packages/accounting/src/fingerprint.ts` and `0045`'s `accounting_canonical_line()` / `accounting_fingerprint()`. The database side builds `BYTEA`, not `TEXT`, because a NULL dimension is the single byte `0x00` and PostgreSQL `TEXT` cannot contain it — faking it with `'\x00'`, an empty string or a literal backslash-zero would make the two implementations disagree on exactly the value most likely to appear in an attacker's payload. Lines are sorted by their own serialized bytes (`Buffer.compare` and BYTEA ordering are both plain unsigned byte comparison), and duplicates both survive, because multiplicity is financial truth.

`accounting_post_entry` recomputes the stream from the payload it was handed and refuses with `accounting.assertion_payload_mismatch` before any write if the result differs from the fingerprint the assertion signed. The signature therefore authorizes a payload, not a number. Idempotency resolves on `(business_id, source_type, source_id)` under a transaction-scoped advisory lock on the source identity: an identical retry returns the original entry with `created=false`, a materially different one raises `accounting.idempotency_conflict`, and neither path ever surfaces a unique-violation to application semantics.

**Tests.** `packages/accounting/vectors/acctfp-vectors.json` is the shared byte-vector suite — the load-bearing one, because without it a refactor re-hashes history silently and every stored fingerprint becomes unverifiable. `packages/accounting/test/fingerprint.test.ts` runs it against the TypeScript implementation and `tests/integration/accounting-fingerprint-parity.test.ts` runs it against the SQL one, so neither can drift without the other failing. `tests/integration/accounting-posting.test.ts` covers the behaviour rows: identical retry, reworded retry (narrative is outside the stream), materially different truth, a retry after the account was deactivated, a retry after the timezone changed. `tests/integration/accounting-concurrency.test.ts` §50 is the concurrent case on two real connections with different assertion JTIs — one entry, one binding, one audit event, one outbox event, the same entry id to both callers.

**P2-S4: the invariant now holds on every source, and once did not.** The rule above is the primitive's, and any command that hands a caller an already-posted entry *without going through the primitive* has to state it again for itself. `accounting_open_balance_post` originally did not: it returned the existing entry as soon as it saw `status = 'posted'`, before proving which command was being retried, so one `Idempotency-Key` re-sent with a different opening position was answered "success" with the old position. It now loads that entry by composite identity `(business_id, journal_entry_id)`, requires it to be this opening balance's own entry, and requires its persisted `posting_fingerprint` to equal the fingerprint `accounting_actor` verified out of the signed assertion — raising `accounting.idempotency_conflict` on any difference. There is no caller-supplied fingerprint parameter anywhere in the slice, by construction and by gate check. `tests/integration/accounting-idempotency.test.ts` is the permanent proof: the nine-way mutation matrix over every `acctfp/1` field, the canonical-equivalence cases that must still replay, the exact retry, and the same three questions asked of the manual adjustment and the reversal. `tests/integration/accounting-sources-concurrency.test.ts` adds the two same-key races. §6a of `PHASE_2_S4_ACCEPTANCE.md` is the full account.

**Related precedent.** Actor-scoped provisioning idempotency, including the "another actor cannot replay or forge" case, is tested at `tests/security/provisioner-boundary.test.ts:317`.

## 8. The FX formula (AL-09)

**Rule.** `fx_rate` means 1 major unit of transaction currency = R major units of base currency. With `rate_scaled = R × 10^10`:

```
numerator   = txn_minor × rate_scaled × 10^max(0, eb − et)
denominator = 10^10 × 10^max(0, et − eb)
base_minor  = HALF_EVEN(numerator / denominator)
```

Half-even by floor-and-remainder comparison (`2r > d`, `2r < d`, `2r = d` → tie to even). No floating point at any step; `BigInt` in TypeScript, `NUMERIC`/`BIGINT` in PostgreSQL, and `ROUND()` is deliberately not used because PostgreSQL rounds half-up and would disagree on ties. Structural completeness is immediate CHECKs on `journal_lines` (exactly one booked side; `base_amount_minor = GREATEST(debit, credit)`; `fx_rate > 0`; domestic lines pinned to `fx_rate = 1` and `fx_rate_source = 'base'`); the arithmetic equality itself is asserted by the deferred validation trigger, because a CHECK may not read `currencies`. Seven pinned vectors, of which cases 5 and 6 are the half-even ties.

**Status: ENFORCED in the database (P2-S2); still SPECIFIED in TypeScript.** `0042` carries the structural half as immediate CHECKs on `journal_lines`: exactly one booked side, `base_amount_minor = GREATEST(debit, credit)` on a domestic line, `fx_rate > 0` declared `NUMERIC(20,10)`, a domestic line pinned to `fx_rate = 1` with `fx_rate_source = 'base'` and no rate timestamp, and a foreign line required to carry the complete snapshot — rate, source and `fx_rate_at` together, never a partial one. `0043` carries the arithmetic: `accounting_assert_entry_valid()` recomputes the expected `base_amount_minor` for every foreign line from both currencies' real exponents in `currencies`, and refuses the entry at COMMIT with `accounting.entry_fx_arithmetic` if the stored value differs by a single minor unit. Half-even is spelled out by quotient and remainder (`2r > d`, `2r < d`, tie → even); `ROUND()` is not used anywhere in `0043`, and `accounting_pow10()` builds its power of ten with `repeat()` rather than `power()` or `^`, both of which return double precision.

**Status update — the TypeScript half landed in P2-S3.** `packages/accounting/src/fx.ts` implements the same formula on `bigint` (`rateScaled`, `convertToBaseMinor`, `isExactConversion`) with the same floor-and-remainder half-even tie rule and no floating point at any step, and `packages/accounting/src/types.ts` exports `MAX_MONEY_MINOR = 10n ** 18n`, which `post.ts` applies to both amounts on every line. "Implemented twice and the two must agree" is now fully met, and the database remains the authoritative one: it refuses at COMMIT whatever the application computed. `packages/accounting/test/fx.test.ts` pins the vectors on the TypeScript side; `accounting-journal.test.ts` pins them on the SQL side.

**Tests.** `tests/integration/accounting-journal.test.ts` pins seven vectors against a real database — USD(2)→ILS(2), JOD(3)→ILS(2), ILS(2)→JOD(3), a large LBP amount, the half-even tie to an even quotient, the tie to an odd quotient, and `MAX_MONEY_MINOR` at rate 1 — each with an accepting case and a case one minor unit away that must be refused. Six structural cases cover the partial-snapshot and domestic-pinning rules.

**Precedent that does exist.** Exact minor-unit money with no float path: `packages/domain-core/src/money.ts` (BigInt only; `Number` accepted solely when `Number.isSafeInteger`; excess precision throws `PRECISION_OVERFLOW`), `packages/shared-contracts/src/money.ts` (`parseMajorToMinor`, exact decimal string parsing). Tested at `packages/domain-core/test/domain-core.test.ts:89`–`:151` and `packages/shared-contracts/test/money.test.ts:10`–`:77`. Guarded statically by `scripts/static-guards.ts` Rule 6 (money as `number`, `Number()` on minor units, float money columns in SQL) and by `tests/golden-regression/phase1/05-artifact-hygiene.golden.test.ts:48` (P1-GOLD-35).

**One gap closed in P2-S2, one still open:**
- **Closed — guard G-2.** Static-guard Rule 6's SQL check keys off column *names* (`amount|price|total|balance`), so `fx_rate DOUBLE PRECISION` would have passed it untouched. `scripts/guards/no-float-rate.ts` is the rate-shaped half: on the journal, the chart and every `accounting_*` table (matched by prefix, so a future accounting table is watched the day it is created), a column with `rate` as a whole underscore token may not be `REAL`, `FLOAT`, `DOUBLE PRECISION`, bare `NUMERIC`, or `NUMERIC` with a scale under 10. It runs as static-guard Rule 16 and has its own tamper regressions in `tests/integration/accounting-guards.test.ts`, including the negative half: a `conversion_rate` on a campaign or a `tax_rate` on a product is not accounting authority and stays declarable, because a guard nobody can live with is a guard that gets deleted. P2-S5 extends the watch list to the FX rate tables it introduces.
- **Still open.** `MAX_MONEY_MINOR = 10^18` and `assertWithinMoneyRange()` (AL-10) do not exist in TypeScript. `MoneyError` already reserves the `PRECISION_OVERFLOW` code, so this is an addition to an existing type, not a new concept. The database enforces the cap now — `journal_lines` CHECKs every minor-unit column into `0 < amount <= 10^18` — but the application does not.

## 9. Error redaction (AL-02, AL-10)

**Rule.** Commit-time failures raise a stable machine code plus safe identifiers only — never debit/credit sums, amounts, rates or balances: `accounting.entry_unbalanced`, `...entry_too_few_lines`, `...entry_business_mismatch`, `...entry_account_foreign`, `...entry_fx_arithmetic`, `...entry_status_invalid`, `...entry_binding_missing`. The earlier proposal to put the two sums in the message is withdrawn. SQLSTATE `22003` maps to `accounting.amount_out_of_range`, never a leaked driver error. Reconciliation tooling that needs the offending sums gets them through an authorized diagnostic path under the normal redaction and audit rules.

**Status: ENFORCED for the codes P2-S2 raises.** `0043` raises exactly the stable codes above — `accounting.entry_missing`, `...entry_status_invalid`, `...entry_business_mismatch`, `...entry_account_foreign`, `...entry_too_few_lines`, `...entry_base_currency_mismatch`, `...entry_unbalanced`, `...entry_fx_arithmetic`, `...entry_binding_missing` — and none of their messages contains a debit sum, a credit sum, an amount, a rate or a balance. The two immutability codes (`accounting.journal_immutable`, `accounting.binding_immutable`) and `accounting.base_currency_locked` follow the same rule. What is still SPECIFIED is the mapping layer: `22003` → `accounting.amount_out_of_range` at the API boundary, and the authorized diagnostic path that gives reconciliation tooling the offending sums. Both belong to the slice that has a posting API.

The redaction architecture this builds on:

| piece | where |

**Tests.** `tests/integration/accounting-journal.test.ts` posts a deliberately unbalanced entry and asserts the message carries `accounting.entry_unbalanced` and neither of the two sums involved; and posts a deliberately wrong FX conversion and asserts the message carries `accounting.entry_fx_arithmetic` and the line number, but not the booked amount, the transaction amount or the rate. `tests/integration/auth.test.ts:147` — error responses never leak secrets, SQL or stack traces.

**Documentation gap, and it matters for this rule specifically.** AL-02 justifies the no-financial-values rule by citing `DAFTAR_OBSERVABILITY.md`. That document says logs carry no secrets and no sensitive data with redaction (line 5); it does **not** say financial values are forbidden in logs or exception messages. The logger's redact paths likewise cover token/secret/password-shaped keys, not amounts. So the rule AL-02 leans on is not actually written down anywhere binding, and nothing tests it. Either add the sentence to `DAFTAR_OBSERVABILITY.md` and a guard alongside static-guard Rule 11, or stop citing the observability document as the authority.

**The one performance invariant this slice could not close.** The permissive `tenant_membership` policy on `journal_lines` is planned as a correlated `EXISTS` per row, where the same policy on `journal_entries` is hashed once, and a whole-business trial balance therefore costs 34× the identical read without the policy (67 866 shared blocks against 724). Isolation is **not** weakened by this — the policy is correct — but budget C misses at 524.0 ms against a 500 ms ceiling, and the repair is to the policy's shape, inside a frozen migration. Recorded as **TD-11**, with the plans in `PHASE_2_PERFORMANCE_BASELINE.md` §5.2.

## Everything I could not find enforced

Stated plainly, because the list is the point of this page. Recompiled after P2-S4; the shrinking is real, but read item 1 carefully before citing anything here as protection.

1. ~~**The whole of posting AUTHORITY**~~ — **closed in P2-S3.** `accounting_post_entry`, `accounting_actor`, `accounting_assertion_keys`, `accounting_assertion_uses`, the canonicalizer in both languages, the posting service and the atomic audit/outbox path all exist and are tested. Read §7 of `PHASE_2_S3_ACCEPTANCE.md` before citing this as protection against any particular attacker: the assertion defends against a stolen `daftar_app` credential, a tampered payload, a replay and a caller-dictated actor, and it does **not** defend against an attacker who has compromised the `merchant-api` process itself, because that process holds the signing key. **Read this next sentence with it:** as first shipped, the stolen-credential claim was false — the credential could not forge a signature, but it could substitute the key table the verifier read, and a forged entry was produced in a test to prove it. That path is closed as of the 2026-09-22 correction, by revoking `TEMPORARY` and `CREATE ON public` from every runtime role and by naming `pg_temp` last in every routine's path, and the exploit is kept as a regression that must be refused. The claim above is now the one the tests actually support.
2. ~~**AL-12 (reversal)**~~ — **closed in P2-S4.** `accounting_post_reversal` derives the mirror from the persisted original and nothing else; `accounting_reversals` makes a second reversal unwritable. Note what it is NOT: it does not defend against an attacker who has compromised the `merchant-api` process, for exactly the reason §7 of `PHASE_2_S3_ACCEPTANCE.md` gives about the signing key — reversal inherits that boundary unchanged.
3. ~~**AL-13 (opening balance lifecycle)**~~ — **closed in P2-S4.** The table, the lines, the three-state machine and the reverse → supersede → replace path all exist and are tested.
4. ~~**AL-01's detail-table delete guard**~~ — **closed in P2-S4** for the two detail tables that now exist: `accounting_manual_adjustments` and `accounting_reversals` both carry unconditional `BEFORE UPDATE OR DELETE` triggers raising `accounting.source_immutable`, and the opening balance's own state trigger permits a delete only from `draft` with no journal identity. The registry-completeness half is stronger than planned: rather than a test enumerating `accounting_source_types`, `0046` and `0047` install **deferred constraint triggers** requiring that an entry of type `reversal` or `opening_balance` carry its detail row by COMMIT, so an entry without one cannot exist even if it were written through the frozen primitive directly. `manual_adjustment` is deliberately excluded: there the journal entry is the whole fact, and the detail row carries only the merchant's narrative.
5. ~~**AL-18's converse**~~ — **closed in P2-S3** as guard **G-4** (`scripts/guards/posting-surface.ts`, static-guard Rule 17, with its own tamper regressions in `tests/integration/posting-surface-guard.test.ts`).
6. ~~**AL-14's enforcement**~~ — **closed in P2-S3** for the date rule and **completed in P2-S6** (migration `0049`, frozen) for periods; see §5. Read the status update there before citing it: the period gate is opt-in by first use rather than universal, because `0049` invents no fiscal calendar, and it narrows what may be posted without ever widening it.
7. ~~**AL-09's TypeScript half**~~ and ~~the byte-vector suite~~ — **closed in P2-S3**: `packages/accounting/src/fx.ts` and `packages/accounting/vectors/acctfp-vectors.json`, the latter run against both implementations.
8. ~~**AL-10's `MAX_MONEY_MINOR`**~~ — **closed in P2-S3**: exported from `packages/accounting/src/types.ts` and applied to both amounts on every line in `post.ts`.
9. **AL-02's "no financial values in errors or logs"** — the P2-S2 and P2-S3 codes honour it and the tests prove it for the journal and the posting path, but the cited authority (`DAFTAR_OBSERVABILITY.md`) still does not contain the rule, and no static guard covers amounts in exception messages outside accounting. The `22003` → `accounting.amount_out_of_range` mapping at the API boundary does not exist.
10. ~~**AL-15's no-balance-column rule**~~ — **closed in P2-S1**: guard G-3 is in CI with its own regression test, P2-S2 added the journal tables to its watch list, and P2-S7 replaced the list with discovery from the schema and added guard G-6 over the read surface. P2-S7 stores no balance of any kind: every reported figure is aggregated from the journal at read time.
11. ~~**AL-02's Matrix 1 as an enumeration**~~ — **closed in P2-S2** as guard G-1.
12. ~~**AL-09's rate column type**~~ — **closed in P2-S2** as guard G-2.

All four guards the lock scheduled — **G-1, G-2, G-3 and G-4** — now exist and run in CI, each with its own regression suite that tampers with a copy of the tree and requires the guard to notice. A fifth, **G-5**, was not scheduled by the lock: review found the defect it exists for, and the guard was written with the fix so the shape cannot come back.

**G-4 changed shape in P2-S4.** It used to protect one named routine, `accounting_post_entry`. The reversal workflow needed a second SECURITY DEFINER journal writer — §5 of `PHASE_2_S4_ACCEPTANCE.md` explains why there was no honest alternative — so the guard now DISCOVERS every routine in the schema whose body writes `journal_entries` or `journal_lines` and requires the whole protection set of each one: a verified actor, fingerprint recomputation, payload-mismatch refusal, the source binding, the audit row, the outbox event, the idempotency lock, SECURITY DEFINER, ownership by the internal principal, EXECUTE revoked from PUBLIC, and a grantee set that is exactly the merchant runtime. A third writer would be held to the same standard on the commit that introduced it.

What remains on this page is genuinely not built, and none of it is authority: it is periods (P2-S6), read models (P2-S7), and one documentation gap. The FX registry left this list in P2-S5, which is now **accepted and frozen** at `0048` — read §7 of `PHASE_2_S5_ACCEPTANCE.md` for what it deliberately does not build (no provider, no reciprocal, no cross-rate, no read endpoint).
