# The road to sealing Phase 4 — the governing plan

**Status.** Approved by the owner on 2026-10-27. Binding on every session until the
seal lands. Where this file and the governance package disagree, governance wins.

**Revised 2026-10-28** for one measured change only: DR-48 made this repository
public, deleted both self-hosted runners and moved all six CI jobs back to
GitHub-hosted machines. That removes the cause of the runner rule in §5 and of
the single-slot queue it implied. §5 now records what was measured; it does not
retire a decision on its own authority. Nothing else in this plan changed.

**Why this file is tracked.** The working copy of this plan lives in
`.local-context/P4_SEAL_PLAN_AR.md`, and `.local-context/` is **not** in the
repository. Anyone who clones this repository therefore sees none of it. DR-24
requires every card, every piece of technical debt and every decision that
touches code to be recorded in a tracked file as well, so the plan that governs
the seal is recorded here. The Arabic working copy stays the day-to-day one; this
is the copy that survives a clone.

## 1. Principles — no exceptions

1. **No PASS without measured evidence**: a real command, its exit code, and a
   run number. An exit code is read from `$?` on a redirected command, **never
   off the end of a pipe** — `cmd | tail` reports `tail`'s status, which is a
   mistake this project has already made and recorded.
2. **A review signature belongs to one commit** and does not carry to a newer
   one. Every round of review that moves the head voids the previous signature,
   which is why review notes are batched (§6) rather than handled one at a time.
3. **One writer per file.** Migrations, `.github/**` and the root `package.json`
   are touched strictly serially.
4. The CI capacity rule (§5) applies as that section states.
5. **Every new defect is classified the moment it is found, with its reason
   written down:**
   - **Seal-blocking** — it touches money, receivables, instalments, security or
     data integrity. Fixed **inside the Phase 4 lineage, before the seal**.
   - **Non-blocking** — a tracked card for after the seal.
   - **Doubtful counts as blocking.**
6. **Scope freeze.** No new feature and no improvement inside Phase 4 from now
   on. Only this plan and blocking defects.

## 4. Wave 3 — the seal branch

Starts only after Waves 1 and 2 have exited.

- **3.1** Create `p4/seal-candidate` from the green `main` and merge the final
  lineage head into it with a **merge commit, not a rebase**. Every conflict is
  documented line by line, and a conflict in a money file is reviewed by
  `daftar-finance`.
- **3.2** Wire `gate:phase4` into `ci.yml`, either on the seal branch itself or
  as a separate `.github` card merged before it — **decided by measurement**, in
  particular the effect of inserting a step on `phase4-s4-gate.ts`, which reads
  the order of `ci.yml`'s steps.
- **3.3 The decisive run**, on the self-hosted runner, in a completely quiet
  window:
  1. Full CI: six jobs pass, **zero skipped**.
  2. Full `gate:phase4`: every slice passes, **none skipped and none NOT_RUN**.
  3. Migrations `0000` → latest, then a no-op re-migration, then history
     verification, with `0074`–`0086` frozen by evidence (DR-03).
  4. **Live evidence on a real database for every money decision**, as a table of
     decision → test → result → run number: C-1, §E, DR-10, DR-13, DR-14, DR-21,
     DR-22, DR-23, DR-27, DR-28, DR-29, DR-30, DR-31, DR-33.
  5. The three timezones for every date test: `UTC`, `Asia/Jerusalem`,
     `Pacific/Honolulu` — all three must pass.
  6. PERF-01: the `p95 ≤ 60 ms` budget **untouched**, its negative control red
     and the ordinary run green.
- **3.4** Every failure is classified. A blocking one is fixed in the lineage,
  re-merged into the seal branch, and then **the whole decisive run is repeated**.
  **No partial re-run counts as seal evidence.**

**Exit:** one complete green decisive run on one commit — the candidate.

## 5. CI capacity — the runner rule (DR-34) and what DR-48 changed

**DR-34, as approved on 2026-10-27.** While `backend` or `browser` was running on
the self-hosted runner, no local test run, build, Docker, `typecheck` or `lint`
was permitted — no heavy `node`, `tsc`, `vitest`, `playwright` or `docker`
process. Reading and writing code, `graphify`, read-only review, documentation,
`git` and preparing pull requests were allowed at any time.

**The rule was a resource rule, not a correctness rule.** The runner was a
service inside a WSL distribution on the owner's laptop, with one job slot. Local
load competed with CI for the same RAM and cores — measured at the time: `backend`
peaked at 4.4 GiB of the distribution's 8.9 GiB, and the `Lint` step alone is
allowed a 6144 MiB V8 heap by the INFRA-02 fix. A long job that lost the runner
was cancelled rather than failed, which is how two runs were lost.

**What DR-48 measured.** On 2026-10-28 the repository was made public, both
self-hosted runners were deleted from it (`/actions/runners` reports
`total_count: 0`), and `.github/workflows/ci.yml` on `main` names
`ubuntu-latest` for all six jobs. GitHub-hosted jobs run on GitHub's machines and
cannot be slowed by this laptop, and the six jobs now run in parallel instead of
queueing behind one slot.

**Consequence, stated and not acted on beyond it.** The premise of DR-34 — a
shared machine — no longer holds for any branch whose `ci.yml` is GitHub-hosted,
and the single-slot queue priority it implied has no subject. Local verification
batches may therefore run while GitHub-hosted CI is in flight. This file records
that measurement; **whether DR-34 is retired, narrowed, or kept in reserve
against a future self-hosted runner is the owner's decision**, and until they
make it the rule stands wherever a self-hosted runner is in use.

**What does not change.** No pull request is pushed before its local
verification has passed (T5), batching review notes rather than pushing one at a
time (§1.2), and one writer per file (§1.3) are unaffected: none of them was a
capacity rule.

The runner as it was built is documented in
`2026-10-27-ci-self-hosted-runner.md`; the move back to GitHub-hosted machines,
and the reverse-migration checklist that is a release blocker, in
`2026-10-28-public-repository-for-ci.md`.

## 7. Wave 5 — the seal dossier

- **5.1** The final dossier: the candidate commit · the decisive run number · the
  evidence table · every decision DR-01…DR-38 · the signatures (internal,
  financial, external) **all on the same commit** · the post-seal card list · the
  remaining risks · and the exact merge command for the owner.
- **5.2 Stop and report.** **Merging to `main` is the owner's decision alone.**
- **5.3 After the owner merges:** verify `main`; close #6, #13, #19 and #21–#25 as
  superseded, with a comment naming the seal commit; archive the branches (**no
  deletion before the owner approves**); refresh `PROJECT_STATUS.md`; and open
  Phase 5 and Phase 7 under DR-05 and DR-19.

## 8. Stop conditions — these and no others

1. **An unsettled product or accounting decision** — one line: the question, the
   two options, the recommendation. **Only the affected path stops.**
2. **A repeated failure that measurement does not explain.**
3. Step 4.3 (the external files) and step 5.2 (the dossier).
4. Context at 70% — save the state, run the wrap-up, and say so.

**Outside these conditions: execute without waiting.**

## 9. Reporting

**One line at the exit of each wave**: the wave, the commit, the run number.
Nothing else.
