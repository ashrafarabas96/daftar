# DAFTAR — UX Architecture / معمارية تجربة الاستخدام

## 1. التنقل

### Mobile (Bottom Navigation — 5 عناصر فقط، Master §5)
الرئيسية · البيع · الطلبات · العملاء · **المزيد**
- "المزيد" تفتح قائمة منظمة: المنتجات، المخزون، الأقساط، المشتريات، الموردون، المصروفات، المتجر الإلكتروني، واتساب، المساعد الذكي، التقارير، الإعدادات — **بتفعيل تدريجي** (تظهر المقاديم المفعّلة أولًا).
- Contextual Navigation داخل كل قسم (Tabs بسيطة مثل: الكل/مستحق اليوم/متأخر).

### Web (التاجر)
Sidebar يمين (RTL): لوحة التحكم، المبيعات، الطلبات، المنتجات، العملاء، المخزون، المحاسبة (تقارير)، التقارير، الإعدادات — وفق الهوية المرجعية (صورة 10).

### Super Admin
Sidebar: لوحة التحكم، المشتركون، المتاجر، الإيرادات، الفوترة، المستخدمون، الدعم، حالة النظام، الإعدادات.

### Storefront (عميل النهاية)
الرئيسية، الأقسام، السلة، الطلبات، المزيد — بحث بارز.

## 1ب. Onboarding (X) — وفق المرجع البصري الرسمي

خمس خطوات مرقّمة بشريط تقدّم علوي: **ترحيب** (مع "تخطي" + **منتقي لغة واجهة فوري عربية/English/Türkçe** — لغة الواجهة مستقلة عن الدولة) → إنشاء حساب (3 حقول + موافقة شروط + رابط دخول) → اسم ونوع النشاط (حقل + Radio cards) → **الدولة + العملة + لغة المتجر** (3 حقول بالضبط؛ لغة المتجر = لغة storefront للعملاء، مستقلة عن لغة واجهة التاجر وعن الدولة، افتراضيها recommended_locale وتُعدَّل لاحقًا بحرية؛ العملة تُقفل بعد أول معاملة مالية) → رابط المتجر بفحص توفر فوري. مبادئ: خطوة واحدة لكل شاشة، Primary CTA واحد ("متابعة"/"ابدأ الآن")، لا حقول غير ضرورية، والقيم الافتراضية الذكية (دولة/عملة/لغة متجر موصى بها من Country Pack) مع بقاء لغات المنصة الثلاث متاحة للجميع (R).

## 2. Core Workflows وعدد الخطوات المستهدف

| المهمة | المسار | الحد الأقصى للخطوات |
|---|---|---|
| بيع نقدي | بحث/مسح → سلة → نقدي → إتمام البيع | 3 قرارات |
| تحصيل دين | عميل → مبلغ → تسجيل الدفعة | 3 |
| طلب يدوي | عميل → منتجات → تأكيد | 3 |
| إضافة منتج | صورة؟ → اسم + سعر (+تكلفة) → حفظ المنتج | 2 حقلان إلزاميان فقط |
| تحصيل قسط | من "مستحق اليوم" → تحصيل قسط → تأكيد التحصيل | 2 |
| أمر صوتي | تحدث → مراجعة العملية → تأكيد العملية | 3 مراحل مرئية (Master §131) |
| Checkout متجر | عنوان + دفع → إتمام الطلب | شاشة واحدة قدر الإمكان |

## 3. Progressive Disclosure (إلزامي — Master §6)

- لا أقساط/فروع/ضرائب/واتساب-تقني لمن لم يفعّلها — تظهر كدعوات بسيطة للتفعيل.
- **Advanced Settings** خلف مستوى ثانٍ (Master §153).
- Smart Defaults آمنة: آخر فرع، العملة الأساسية، طريقة الدفع الأكثر استخدامًا — **لكن لا Defaults في قرارات مالية خطرة** (Master §11).

## 4. قواعد التعقيد (Complexity Rules)

1. Complexity Budget لكل شاشة: كل Button/Tab/Filter/Field يبرر وجوده أو يُحذف/يُنقل (Master §4).
2. One Primary Action مرئي خلال ثوانٍ لمستخدم تجريبي دون شرح (Master §8, §151).
3. لا Confirmation إلا لـ: Financial commit / Destructive / High-risk / AI financial (Master §154).
4. لا حقول يمكن استنتاجها (Master §152)؛ لا حقول إلزامية بلا سبب.
5. Dashboard: الأهم أولًا — مبيعات اليوم، طلبات جديدة، ديون مستحقة، أقساط مستحقة، مخزون منخفض، إجراءات سريعة (Master §123). لا تعرض كل الأرقام مرة واحدة.
6. Search First في القوائم الكبيرة (Master §12).

## 5. أنماط الثقة والحالات

- نتيجة العملية المالية: SUCCESS / FAILED / PENDING SYNC + مرجع (Master §15).
- No False Success قبل commit الخادم (Master §161).
- رسائل الخطأ: ماذا حدث؟ هل بياناتي محفوظة؟ ماذا أفعل؟ — ممنوع "Error 500" العاري (Master §14).
- Empty States حيّة بـCTA (Master §13).
- Loading: skeletons وcached content؛ لا loader مزعج للعمليات القصيرة (Master §159–160).
- Plan Limit UX: عند بلوغ حد الباقة — سبب + حد + استخدام + Upgrade، بلا إتلاف بيانات (Master §121).

## 6. AI UX

- المساعد جزء أصيل بصريًا (نفس Cards/Typography — Master §130).
- ثلاث مراحل: الاستماع → مراجعة العملية (ما فهمه AI معلنًا بالكامل — Master §132) → تم.
- Confirmation صريح لأي mutation مالية (Master §53).
- الغموض (عميلان متشابهان) = سؤال، لا تخمين (Master §51).

## 7. إمكانية الوصول

- تباين AA، أهداف لمس ≥ 44px، نصوص واضحة، دعم قارئ الشاشة للعناصر الأساسية، وعدم الاعتماد على اللون وحده في الحالات الدلالية.
