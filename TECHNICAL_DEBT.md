| TD-09 | The refusal of a FUTURE-dated journal entry lives in the three posting commands (`accounting.entry_date_in_future`, migrations 0045/0046/0047), not in a schema constraint. Raw SQL by the schema owner can insert an entry dated in the future | Not a security or data-integrity defect and not reachable by any application path: every writer of the journal goes through a command, `daftar_app` holds no INSERT on `journal_entries`, and the raw-SQL matrix (`tests/security/accounting-raw-sql-invariants.test.ts`) asserts BOTH halves — the commands refuse it and the schema does not. It is a missing layer of defence in depth, discovered by P2-S8's raw-SQL matrix, not a hole in the wall | None reachable today; a future migration that writes the journal directly, or a new trusted routine, would not inherit the rule | **Repayment shape decided in P3-S0 (`docs/PHASE_3_ARCHITECTURE_LOCK.md` P3-AL-36): a `BEFORE INSERT` trigger on `journal_entries`, not a CHECK constraint.** A CHECK states a timeless row invariant, and `entry_date <= CURRENT_DATE` is a statement about the **moment of insertion**, so a row that was legal when written stays legal forever — something a CHECK cannot express. Its truth value would change underneath committed rows, so `ALTER TABLE … VALIDATE CONSTRAINT`, a `pg_dump` reload or any later revalidation could reject data the database itself accepted. And the rule is “not in the future **in the business's own timezone**”, which requires reading `businesses.timezone`; a CHECK may not read another table at all, which settles the mechanism on its own. (An earlier wording claimed PostgreSQL refuses `CURRENT_DATE` in a CHECK outright. **That is wrong and is withdrawn** — measured on PostgreSQL 16, `CHECK (d <= CURRENT_DATE)` is accepted at `CREATE TABLE`; PostgreSQL only *assumes* immutability and warns about the consequences. The decision rests on semantics and the cross-table dependency, not on a parser restriction.) The trigger instead resolves the BUSINESS's timezone, computes the current civil date there, refuses a future `entry_date` with the same stable `accounting.entry_date_in_future` the commands already raise, and carries no financial values in its message. `0049_accounting_periods.sql` already attaches `accounting_period_guard` to `journal_entries` the same way, so the pattern is precedented and no frozen byte changes. The command-level checks REMAIN — this is defence in depth beneath them, not a replacement. **Target: P3-S1, the first authorized schema slice of Phase 3.** The boundary while it is open is exact: the only principal that could insert such a row is the schema owner, which is the DEPLOYMENT credential — a credential no service loads, that appears in no runtime connection URL, and whose holder can already alter the schema at will. There is no runtime path to this, so leaving it open permits no corruption a deployment credential could not cause anyway | **repaid by the P3-S1 candidate `0058_accounting_entry_date_guard.sql`** (the `BEFORE INSERT` trigger, `SECURITY DEFINER` owned by `daftar_accounting_internal`; the raw-SQL matrix now asserts both halves refuse), closed on Tech Lead acceptance of P3-S1 |
| TD-10 | Accounting assertions are signed with a symmetric HMAC whose secret is held by the merchant API process (`ACCOUNTING_ASSERTION_KEY`); the KMS review (`docs/PHASE_2_KMS_SIGNER_REVIEW.md`) did not close the boundary | Not a defect: the current design is the one that was accepted, and the review's own conclusion is that moving HMAC signing behind a KMS does not remove the secret from the trust boundary — it moves it from the API process to PostgreSQL. Only asymmetric signing removes it, and `pgcrypto` cannot verify Ed25519, so the change is a redesign, not a configuration | A process compromise that reads the API's environment can mint assertions until the `kid` is retired | Escalated to the Tech Lead as a design decision: adopt asymmetric assertion signing (sign in the API or a signer service, verify in the database with a public key), which needs a verification primitive PostgreSQL does not ship today. **Tech Lead decision for Phase 3, recorded 2026-09-25 (`docs/PHASE_3_ARCHITECTURE_LOCK.md` P3-AL-37): KEEP the currently accepted symmetric HMAC design. `ACCOUNTING_ASSERTION_KEY` remains EXCLUSIVE to `merchant-api` — not the worker, not `platform-api`, no second signer — because Phase 3 introduces no second signing process and all Phase 3 financial posting happens inside `merchant-api`'s accepted trust boundary. The accepted database verifier is NOT redesigned during Phase 3. This decision does not close the debt and must not be read as closing it: nothing about the boundary was solved, only bounded. Any future phase that would expose assertion signing to a second process must reopen TD-10 for architectural review BEFORE doing so.** The original repayment remains: adopt asymmetric assertion signing when a verification primitive exists. The boundary while it is open is exact: an attacker must already be executing inside the merchant API process, where they can read `ACCOUNTING_ASSERTION_KEY` from the environment. That is not a runtime authority escalation — a process that can read the key can already call the posting command with the API's own credential — and it permits no corruption of what is already written, because the journal is append-only and every entry carries its own fingerprint. Rotating the `kid` retires every assertion minted with the stolen key | open (decision, P2-S8 review; Phase 3 boundary decided 2026-09-25, debt NOT closed) |

| TD-13 | The opportunistic prune of expired assertion uses in the **frozen** `provisioning_assertion_consume` path (`0038_provisioning_assertions.sql:135`) and the accounting posting path (`0045_accounting_post_entry.sql:233`) is a plain `DELETE`, which row-locks every expired use it touches, so a consuming transaction left open makes other consumers of the same domain, in any tenant, wait until it ends.
