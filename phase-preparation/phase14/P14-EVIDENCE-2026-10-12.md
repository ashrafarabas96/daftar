## 3. The laws, as executed

### `C1` — the `WHERE`-clause privilege (V2 FINDING 2)

PostgreSQL requires `SELECT` on a column a query **restricts on**, not only on
one it returns. Under a grant of `(key_id, id, business_id, name)` the resolver's
lookup by `secret_sha256` is refused with **`SQLSTATE 42501`**, while the same
role reads the columns it was granted — so the refusal is about the restricted
column and not about table access. With the lookup column granted, the read
returns the row. Withdrawing `secret_sha256` alone turns that arm red (`C1c`,
exit 3).

### `C2` — an absent privilege is not a mechanism (V2 FINDING 3, `P14-AL-37`)

With a narrowed `SELECT` and an unqualified `GRANT INSERT`, the merchant role
**successfully inserted a `secret_sha256` and a `subject_user_id` of its own
choosing** — a forged working key, written by a role that cannot read a single
digest back. With `INSERT` column-scoped the same statement is refused with
`42501`, and re-widening the grant turns the refusal arm red (`C2c`, exit 3).
This is the most serious defect in the pack's history and the fix is correct.

### `C2d` — a NEW finding against this pack's own §11.1

The column-scoped merchant `INSERT` set is **not satisfiable**. Omitting the
columns outside it is refused with `23502`, and supplying them with `42501`:
both branches closed. Note that the constraint which fired first was
`subject_user_id`, **not** the `secret_sha256` the case was written to test — so
the second branch was executed separately rather than inferred, because a
refusal test that asserts only "it failed" can pass on the wrong constraint.
Key creation therefore cannot be a direct merchant `INSERT` at all. **A grant
matrix must be satisfiable as well as safe, and nothing in this pack asserted
that until it was run.**

### `C3` — a PERMISSIVE policy is inert against a RESTRICTIVE one (§11a's premise)

With the accepted `business_isolation` text verbatim **plus** an added PERMISSIVE
policy admitting the context-free worker, the pre-context read returns **0
rows** — the premise `TL-P14-SEC-01` rests on, now executed rather than
reasoned. With the disjunct added to the RESTRICTIVE `USING` **only**, the
worker reads 2 rows and both an `INSERT` and an `UPDATE` are refused by
`WITH CHECK` with `42501`. **So the stricter variant this pack recommends to the
Security Owner works as described: reads admitted, cross-business writes
refused.** Re-adding the disjunct turns the 0-row arm red (`C3c`, exit 3).

### `C4`, `C5` — the usability predicate and its boundary

Unparenthesised, `A OR B AND C OR D` **accepts a key that expired 365 days ago**;
parenthesised it refuses it, and the usable set is then exactly the one live key.
At exactly `expires_at`, `>` refuses and `>=` would accept — the two arms differ
by exactly that key — and the neighbours one microsecond either side settle the
direction.

### `C6` — no invariant depends on a clock that keeps moving (`P14-AL-35`)

Under a `BEFORE UPDATE` guard derived from `now()`, renaming a key whose
revocation instant has passed is refused with `23514`, although the write touches
nothing the invariant is about. Scoped to intent changes, the rename succeeds,
un-revoking is refused, moving the revocation later is refused, and moving it
earlier is accepted.

### `C7` — the source-outbox binding (`TL-P14-SEC-02`)

Three results, and together they **change the ruling request** — see §7a of the
patch request, now rewritten as four costed options:

1. The writer was given **no `SELECT` at all** on `outbox_events` (fenced
   refusal, `42501`) and the cross-business parent link was **still accepted**.
   FK enforcement does not consult the writer's privileges.
2. The proposed non-`SECURITY DEFINER` assertion is **inoperable as written**:
   invoker rights mean it cannot read the parent, so it refuses the
   **same-business** write too (`42501`). It fails closed and is unusable.
3. Granting the read makes it work exactly as designed — cross-business refused
   `23514`, same-business accepted, `NULL`-business platform event refused — at
   the measured cost of that role reading **2 rows belonging to another business
   or to the platform**, because `outbox_events` carries no RESTRICTIVE policy.

### `C8` — rotation and revocation across four instants

Evaluated at a **fixed** instant `T`, never at a moving `now()`: usable at
`T-1d` and `T-1µs`, not usable **at** `T`, not usable after — and
`revoke_scheduled` is **still `true`** afterwards, which is the law this pack
states: the boolean does not become false on its own and a passed schedule **is**
a revocation. The replacement key is usable across all four instants, so the
overlap window is real. The composite rotation link refuses a cross-business
predecessor with `23503`, and a `NULL` link is accepted — a first key replaces
nothing.

### `C9` — the challenger's P1-01, and its resolution

Under §3's eight-column grant verbatim, §1's ten-column resolver `SELECT` is
refused with **`42501`**: *the authentication path refuses every request.* Each
omitted column was isolated as a cause. **The resolution is EIGHT, not ten, and
the defect was in §1 and §11.1 rather than in §3**: `P14-AL-11` forbids any
reader consulting `revoke_scheduled` to decide usability, and a resolver that
selects it is a reader of it — so the earlier revision forbade and required the
same read in one pack. `name` is management data the business transaction already
holds. The eight-column query and the predicate both execute (`usable = t`), and
withdrawing `secret_sha256` turns that arm red (`C9c`, exit 3) — the red proof
for the auth query the challenge required.

## 4. The two runs that were wrong, kept rather than deleted

**`C3-SETUP` first attempt, exit 3.** The fixture's own seed `INSERT` was refused
by `FORCE ROW LEVEL SECURITY`, which applies to the table owner too. The seeds
were moved before the `FORCE` statement.

**`C3-FENCE` first attempt, exit 3 — and it produced a finding.** The fence read
as owner with `app.bypass_rls = 'on'` and saw **0 rows**, which looked like a
broken fixture. It is not: **`app.bypass_rls` relaxes only the RESTRICTIVE
half.** A caller still needs a PERMISSIVE policy to admit it, and neither
`tenant_membership` (no `app.tenant_id` set) nor `worker_delivery` (wrong
`current_user`) admitted the owner. **So bypass alone is not a god-mode read on
this idiom** — the same lesson as `C3`, in the other direction. The fence now
sets `app.tenant_id` as well.

**Why both are in this document.** `C3a` asserts an **absence** — 0 rows. It had
passed against an **empty table**, which settles nothing. Only the failing fence
revealed that, and the law was re-run against a table proved to hold 2 rows.
An unfenced ABSENT result is not evidence, and a case that cannot tell "refused"
from "nothing there" will pass for the wrong reason.
