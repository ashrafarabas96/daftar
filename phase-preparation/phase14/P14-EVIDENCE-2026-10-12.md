## 3. The laws, as executed

### `C1` — the `WHERE`-clause privilege (V2 FINDING 2)

PostgreSQL requires `SELECT` on a column a query **restricts on**, not only on
one it returns. Under a grant of `(key_id, id, business_id, name)` the lookup by
`secret_sha256` is refused with **`42501`**, while the same role reads the
columns it was granted — so the refusal is about the restricted column, not
about table access. With the column granted, the read returns the row.
Withdrawing `secret_sha256` turns that arm red.

### `C2` — an absent privilege is not a mechanism (V2 FINDING 3, `P14-AL-37`)

With a narrowed `SELECT` and an unqualified `GRANT INSERT`, the merchant role
**wrote a `secret_sha256` and a `subject_user_id` of its own choosing** — a
forged working key, by a role that cannot read a single digest back. Column-scoped,
the same statement is refused with `42501`; re-widening the grant turns the
refusal arm red. The scoped column set in that case is **illustrative and says
so in its own comment**, because §11.1's `INSERT` cell is not enumerated (§11.1a).

### `C2d` — a finding against this pack's own §11.1

The column-scoped merchant `INSERT` set is **not satisfiable**: `23502` without
the columns outside it, `42501` with them. The constraint that fired first was
`subject_user_id`'s, **not** the `secret_sha256` the case was written to test,
so the second branch is executed separately rather than inferred — a refusal
test asserting only *"it failed"* can pass on the wrong constraint. Key creation
cannot be a direct merchant `INSERT` at all. **A grant matrix must be
satisfiable as well as safe.**

### `C3` — a PERMISSIVE policy is inert against a RESTRICTIVE one (§11a's premise)

With the accepted `business_isolation` text verbatim **plus** a PERMISSIVE policy
admitting the context-free worker, the pre-context read returns **0 rows** — the
premise `TL-P14-SEC-01` rests on. With the disjunct in the RESTRICTIVE `USING`
**only**, the worker reads 2 rows and both `INSERT` and `UPDATE` are refused by
`WITH CHECK` with `42501`, so the stricter variant this request recommends works
as described. Re-adding the disjunct turns the 0-row arm red.

### `C4`, `C5` — the usability predicate and its boundary

Unparenthesised, `A OR B AND C OR D` **accepts a key that expired 365 days ago**;
parenthesised it refuses it, and the usable set is then exactly the one live key.
At exactly `expires_at`, `>` refuses and `>=` would accept; the neighbours one
microsecond either side settle the direction.

### `C6` — no invariant depends on a clock that keeps moving

Under a guard derived from `now()` on every `UPDATE`, renaming a key whose
revocation instant has passed is refused with `23514`, although the write touches
nothing the invariant is about. Scoped to intent changes: the rename succeeds,
un-revoking is refused, moving the revocation later is refused, moving it earlier
is accepted.

### `C7` — the source-outbox binding (`TL-P14-SEC-02`)

1. The writer was given **no `SELECT` at all** on `outbox_events` (fenced
   refusal, `42501`) and the cross-business parent link was **still accepted** —
   FK enforcement does not consult the writer's privileges.
2. The non-`SECURITY DEFINER` assertion is **inoperable without a read grant**:
   invoker rights mean it cannot see the parent, so it refuses the
   **same-business** write too. Fails closed, unusable.
3. **With the grant it works exactly as designed** (`c7b_refused_after_grant`,
   exit 0): cross-business refused `23514 OUTBOX_EVENT_BUSINESS_MISMATCH`,
   same-business accepted, and the `NULL`-business platform event refused because
   `IS NOT DISTINCT FROM` does not match `NULL`. **This green run is new in
   round 2 and the challenger was right that it was missing**: §7a's central law
   previously had no passing run anywhere in the pack, only two refusals that
   predated the grant making the assertion operable. It is the strongest single
   piece of evidence for `TL-P14-SEC-02`.
4. The cost of that grant, measured in the same replay: the role then read **2
   rows belonging to another business or to the platform**, because
   `outbox_events` carries no RESTRICTIVE policy. **But see §7a as rewritten in
   round 2 — if the delivery principal is `daftar_worker`, that grant already

### `C8` — rotation and revocation across four instants

Evaluated at a **fixed** instant `T`: usable at `T-1d` and `T-1µs`, not usable
**at** `T`, not usable after — and `revoke_scheduled` is **still `true`**
afterwards, which is the law: the boolean does not become false on its own and a
passed schedule **is** a revocation. The replacement is usable across all four
instants, so the overlap window is real. The composite rotation link refuses a
cross-business predecessor with `23503`; a `NULL` link is accepted, since a first
key replaces nothing.

**The constraint that produces that refusal is now created by
`c8_setup_fk.sql`, which ends by reading `pg_get_constraintdef` and refusing to
proceed unless the definition names `business_id`.** In the first edition it was
an ad-hoc command, so this case's exit 0 was unreproducible — the single
worst defect in that edition and entirely mine.

### `C9` — the eight-column resolver

Under §3's eight-column grant verbatim, the ten-column resolver `SELECT` is
refused with **`42501`** — the authentication path refuses every request — each
omitted column isolated as a cause. The resolution is **eight**, on `P14-AL-29`:
a boolean of intent is *never read to decide usability*, and the resolver's only
purpose in reading the row **is** to decide usability. The qualifier matters and
round 2 restored it: without it the rule would invalidate §11.1's own grant of
this column to `daftar_app`, which the management surface needs. The eight-column
query and the predicate both execute (`usable = t`); withdrawing `secret_sha256`
turns that arm red — the red proof for the auth query.

## 4. Runs that were wrong, kept rather than deleted

Both belong to the **first** edition and neither recurs in this replay. They are
kept because each taught something.

**`c3_setup` first attempt, exit 3.** The fixture's own seed `INSERT` was refused
by `FORCE ROW LEVEL SECURITY`, which applies to the table owner too. The seeds
moved before the `FORCE` statement.

**`c3_fence` first attempt, exit 3 — and it produced a finding.** The fence read
as owner with `app.bypass_rls = 'on'` and saw **0 rows**, which looked like a
broken fixture. It is not: **`app.bypass_rls` relaxes only the RESTRICTIVE
half.** A caller still needs a PERMISSIVE policy to admit it, and neither
`tenant_membership` (no `app.tenant_id`) nor `worker_delivery` (wrong
`current_user`) admitted the owner. **Bypass alone is not a god-mode read on this
idiom** — the same lesson as `C3`, in the other direction.

**Why that matters more than either run.** `c3a` asserts an **absence** — 0 rows
— and it had first passed against an **empty table**, which settles nothing.
Only the failing fence revealed it. An unfenced ABSENT result is not evidence,
and a case that cannot tell *"refused"* from *"nothing there"* passes for the
wrong reason. **Round 2's P1-02 is this same lesson one case over, unapplied: a
refusal arm whose constraint is never proved present is an unfenced PRESENT
result.** The fix is the same in both directions — prove the state, then read
the outcome.
