## 5. Findings

### P1-01 — §3 grants EIGHT columns to `daftar_identity` while §1 and §11.1 require TEN, and the gate written for this class cannot see it

**This is the third consecutive recurrence of the species that V3 FINDING 1
identified, inside the fix for it.**

Amendment 05 FINDING 1 found that §1 derived a ten-column resolver set and §11.1
granted eight, and states the fix: *"§11.1 now carries the ten columns."* It does
— §11.1's `daftar_identity` row reads *"ten columns, matching §1 exactly."*

**§3 was not touched.** `P14-MIGRATION-PATCH-REQUEST.md` §3 still carries, as its
own DDL, the statement a migration author copies:

```
GRANT SELECT (business_id, id, tenant_id, key_id, secret_sha256,
              subject_user_id, expires_at, revoked_at) ON api_keys
  TO daftar_identity   -- "exactly those eight columns"
```

and, worse than an oversight, it **argues** for eight on security grounds:
*"`name`, `created_by_user_id`, `revoked_by_user_id`, `revoked_reason` and
`last_used_at` are management data the resolver has no reason to read, and a
column it cannot read is a column it cannot leak."* §1 lists `name` ("audit and
error context") and `revoke_scheduled` ("displayed as intent") as resolver
columns. So the two sections do not merely differ in a list — they give opposite
reasons for opposite grants.

**Executed (E4), PostgreSQL 16.15 @ `en_US.utf8`, as non-superuser
`daftar_identity`.** Under §3's grant, verbatim, the §1 resolver's own `SELECT`
list:

```
SELECT key_id, id, tenant_id, business_id, subject_user_id, secret_sha256,
       expires_at, revoked_at, revoke_scheduled, name
FROM api_keys WHERE key_id = '…';
→ ERROR:  permission denied for table api_keys
```

isolated per omitted column:

```
SELECT name             FROM api_keys WHERE key_id = '…';  → ERROR: permission denied
SELECT revoke_scheduled FROM api_keys WHERE key_id = '…';  → ERROR: permission denied
```

**The authentication path, implemented from §3, refuses every request.**

**Why the pack's own machinery does not catch it, which is the real finding.**
Three mechanisms were supposed to:

1. §11's self-declared authority — *"where a section's prose and this table
   disagree, the migration is not written until the request is corrected."*
   That resolves the contradiction **only for a reader who notices it**. §3 is
   not prose about grants; it **is** a `GRANT` statement with a security
   rationale, which is the form a migration author implements.
2. `P14-GATE-033`, written for exactly this class, is scoped in both
   `P14-AMENDMENT-05` §3 and `P14-TASK-DAG.md:191` as *"§1's resolver columns
   and §11.1's grant equal in both directions."* §3 is **outside its stated
   scope**. The gate passes while the defect stands.
3. §14's catalogue test asserts `information_schema` against **§11**. If the
   migration is written from §3, the catalogue and §11 disagree and the test goes
   red — which is a real backstop, but it fires **after** the migration is
   written, and its most likely repair is to widen the grant to make an error go
   away, which §1 names as forbidden (`P14-AL-29`).

**Required before DDL — and the correct fix is not simply "copy ten into §3".**
The two sections disagree on a *security* question that is still open: does the
pre-context resolver need `name` and `revoke_scheduled` at all? §3's argument is
the better one. `name` is error context that can be fetched in the business
transaction, and `revoke_scheduled` is explicitly *"never read to decide
usability"* — granting both to the one role that can read every key row's digest
across every business widens the blast radius of the pack's most privileged
principal for no authentication purpose. So:

- **settle which eight-or-ten is right**, on §1's own stated rule (*"the column
  set follows from the query, the query is stated here"*) — and if the resolver
  does not use `name` and `revoke_scheduled`, the defect is in **§1 and §11.1**,
  not in §3;
- then make all **three** sections equal, and
- **restate `P14-GATE-033` to assert every section that names a grant for a
  relation**, not a named pair of sections. A gate that enumerates its sources by
  name will be blind to the next section added — which is precisely how this
  defect arrived.

### P2-02 — the cashier-escalation finding's evidence is wrong at the declared base, and the error understates the blast radius

Amendment 05 FINDING 2 and §11.8 both assert: *"`BUILTIN_ROLE_PERMISSIONS` gives
the **cashier** exactly `['catalog.view']` (`permissions.ts:149`) and
`inventory.view` only to manager and owner (`permissions.ts:144`)."*

Measured at `93084f8`:

- `permissions.ts:144` is inside `SENSITIVE_PERMISSIONS`, not a role list.
  Manager's `inventory.view` is at **`:179`**.
- `permissions.ts:149` is `isSensitivePermission()`. The cashier is at **`:214`**.
- The cashier does **not** hold `['catalog.view']`. It holds **five**:
  `['catalog.view', 'sales.view', 'sales.create', 'customers.view',
  'payments.collect']`.

The likely origin is the comment at `:206` — *"APPENDED after the accepted
`['catalog.view']`, which is not altered"* — which describes the **Phase 1**
cashier set as it was before Phase 4 appended to it. A historical set was read as
the current one.

**The conclusion survives: the escalation was real.** The cashier does not hold
`inventory.view`, so mapping `GET /stock` to `catalog.view` would have let a
cashier-delegated key read stock the cashier cannot. `P14-AL-39` and
`P14-GATE-032` are correct and should stand.

**What does not survive is the reasoning built on the false premise.** Four of
the cashier's five permissions — `catalog.view`, `sales.view`, `sales.create`,
`customers.view` — are **published v1 scopes**, and one of them is a **write**
(`POST /sales`). A cashier-delegated key therefore reaches four of the six v1
scopes and can commit sales through the public API. That is *not* an escalation —
it mirrors the cashier's real application authority, and the `membership ∩
scopes` intersection is doing its job — but a pack that believes the cashier
holds a single read permission has reasoned about the **narrowest** delegating
principal and its public blast radius from a premise that is false. Every place
the pre-mortem, the attack matrix or the §11.8 commentary leans on "the cashier
can only read the catalogue" needs re-reading against `:214`.

**Required:** correct the two line numbers and the permission list; re-derive any
statement about what a cashier-delegated key can reach; and state the
`sales.create` reachability explicitly, because a key that can *commit a sale* is
the single most consequential thing a delegated v1 key can do and the pack
nowhere says so in those words.

### P2-03 — §12's trigger table omits two triggers the pack commits to, and overstates a third

§12 is titled *"Triggers and functions"* and is the enumeration a migration
author implements. It lists five triggers. Three commitments made elsewhere in
the same request are not in it:

1. **§7a's source-outbox business assertion** — the `BEFORE INSERT` trigger on
   `webhook_deliveries` comparing the source event's business to the delivery's
   own, with its stated non-`SECURITY DEFINER` property and its `NULL`-business
   refusal. It is the entire proposed enforcement for `TL-P14-SEC-02` and it is
   **absent from §12**.
2. **§7a's immutability of `outbox_event_id`, `endpoint_id` and `business_id`**
   after insert — *"so a delivery cannot be re-pointed at another source,
   endpoint or business once the fact exists."* §12's
   `webhook_delivery_payload_immutable` freezes **`payload` only**. §14 tests the
   re-point refusal of all three columns, so the test roster expects a trigger
   §12 does not create.
3. §12 states `webhook_delivery_payload_immutable` as *"the projected payload is
   frozen"*, flat. §7 requires that same trigger to **permit one transition** —
   the purge authority clearing `payload` — and warns that otherwise *"the purge
   cannot run and the trigger would be weakened later to let it."* §12 as written
   is the version §7 predicts will be weakened later.

This is the same species as P1-01 and as V3 FINDING 1: a commitment correct where
written, absent from the section that executes it. §11b's "context-free read"
column points at the §11a ruling for `webhook_deliveries`, so no DDL is written
for it yet — which limits the damage, not the defect.

**Required:** §12 enumerates every trigger the request commits to, including the
purge exception as an explicit permitted transition, before the §7a/§11a rulings
return.

### P2-04 — an unapproved hard-coded threshold survives in §3, the species the withdrawn `300s` established

`P14-HANDOFF-MANIFEST.md` §5 states: *"No timing or performance number appears
anywhere in the pack (PART 10/16)."* §3 contains one:

> *"`last_used_at` is written at most once per key per **5 minutes**, outside the
> business transaction."*

This is a write-rate threshold with a chosen value, no decision record, no
`OD-P14-NN`, and no statement that it is configuration. It is the identical shape
to the `300s` freshness value that Mission FIX 6 struck **by name** and that
Directive 11 PART 97 forbids (*thresholds are configured and never guessed*) —
and, by coincidence of units, the same quantity.

It is also not harmless. The value sets how stale `last_used_at` may be, and
`last_used_at` is what a merchant reads to answer *"is this key still in use, can
I revoke it?"* A guessed staleness window on a revocation-decision signal is an
operational value, not an implementation detail.

**Required:** make it a configured value with no default, under `OD-P14-09`'s
sibling or an explicit new decision, or state that the rate is unspecified. And
correct the manifest's §5 sentence, which is false as written.

### P3-05 — the global-FK species is disclosed for one column and not for three

§7a correctly raises `webhook_deliveries.outbox_event_id → outbox_events(id)` as
a global FK from a business-scoped child, and proposes a trigger plus a ruling.
The same shape appears three more times and is **nowhere disclosed**:

- `api_keys.subject_user_id → users(id)` — **the delegating member whose live
  permissions become the key's authority**;
- `api_keys.created_by_user_id`, `api_keys.revoked_by_user_id → users(id)`;
- `webhook_endpoints.created_by_user_id → users(id)`.

**Executed (E7).** A `subject_user_id` naming a user with no membership in the
key's business is accepted by the schema: the row inserts, no constraint fires.

**It fails closed at runtime**, and that is why this is P3 and not P1: effective
authority is `live_membership_permissions ∩ key_scopes` computed per request for
`(subject_user_id, business_id)`, so a subject with no membership in that
business yields an empty intersection and a powerless key (`P14-AL-02`). The
defence is real.

But it is a **single** application-layer defence on the pack's most load-bearing
column, with no database invariant and no disclosure, in a request that
disclosed the identical species one section earlier and escalated it to three
owners. `subject_user_id` deserves at least the same treatment: either a
membership-binding trigger or an explicit statement that the intersection is the
only guard and why that is sufficient.

### P3-06 — the extended RESTRICTIVE policy's `USING` governs `DELETE`

§3's extended `business_isolation` is `FOR ALL` with
`USING (app_bypass() OR current_user = 'daftar_identity' OR business_id::text =
app_business())` and a `WITH CHECK` that correctly omits the disjunct. `WITH
CHECK` does not apply to `DELETE` — a `DELETE` is governed by `USING` alone. So
the policy, as written, places **no business isolation on a `DELETE` by
`daftar_identity`**.

Nothing is exploitable today: §11.1 grants `DELETE` to nobody, and E6 confirms
`daftar_identity` is refused even an `UPDATE` by privilege. But the isolation of
this one role now rests entirely on a grant never being widened, in a policy whose
stated purpose is to be the second line of defence. Scoping the identity disjunct
to `FOR SELECT` costs nothing and removes the dependency.

### P3-07 — the manifest misdescribes the file it hashes

`P14-HANDOFF-MANIFEST.md` §2 describes `P14-S0-ARCHITECTURE-LOCK.md` as

(`P14-AL-38` at `:648`, `P14-AL-39` at `:659`). The hash is correct; the
description of what it covers is stale. In a handoff manifest — the one document
